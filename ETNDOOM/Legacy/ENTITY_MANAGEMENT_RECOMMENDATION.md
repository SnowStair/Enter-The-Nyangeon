# Entity Management Recommendation / 实体管理与 DOOM 兼容建议

> Status / 状态：全面实体管理架构仍待确认，未实现；阶段 5/7 的敌怪重做前提与 D06 最小玩家接管方案已由用户确认，阶段 1 契约未裁定。
> Scope / 范围：ETNDOOM 模式拥有的实体、更新任务，以及未来 DOOM WAD 的兼容边界。
> Source / 来源：用户 2026-10-23 对兼容收益、DOOM 局限与重做成本的讨论要求，以及 2026-10-24 补充的阶段 5/7 敌怪重做前提与 D06 方案确认；引用聊天「分析 DOOM 实体管理」及本地 `linuxdoom-1.10` 源码复核。
> Date / 日期：2026-10-24（初稿：2026-10-23）

## 1. Recommendation / 建议

建议逐步建立 ETNDOOM 自有的实体生命周期和控制入口，借鉴 DOOM 的玩家与身体分离、统一更新入口、共享类型定义和空间查询职责；为地图相关行为保留可核对的 DOOM 语义。

不建议现在全面移植 DOOM 的运行时，也不建议把原版 `Player`、敌人和子弹全部接入一个新管理器后宣称完成改造。决定采用新玩家控制器，与决定重做所有实体系统，是两项独立决策。

优先目标建议为：让明确支持范围内的经典 DOOM / DOOM II 地图在 ETNDOOM 规则下可用，并逐项验证关键交互。若以后要求原版逐 tic 行为或 demo 同步，应作为更严格的独立项目评估，不能承诺只更换规则配置即可实现。

“所有实体”先限定为当前 ETNDOOM 模式拥有的玩家、敌人、弹丸与拾取物；本体 autoload、其它模组和原模式实体不自动纳入。以下模块名称均为职责示意，不冻结类名、接口或目录。

### 1.1 Enemy Redesign Premise / 敌怪重做前提

用户补充（2026-10-24，来源：user）：为适配 DOOM 地图与 DOOM 的逻辑，阶段 5 与阶段 7 涉及的 ETN 原版敌怪必然大幅重做，或者直接设计新的敌怪。因此，接管原版敌怪既有运行行为没有必要作为新实体管理器的目标；应围绕重做或新设计的敌怪建立行为、生命周期与空间接口。

“新增管理器不会自动取得原实体行为所有权”仍是复用原实例时的技术事实，其适用范围是实际保留的原脚本、组件和全局消费者。它不构成要求新系统整体接管原版敌怪的理由，也不应据此把逐个迁移原版敌怪列为必做工作。美术、音效、配置和可独立复用的部分可按需要评估。

重做成本应以“敌怪本就需要适配 DOOM 地图与逻辑”为基准，比较在此基础上建立新实体管理职责的增量成本与收益；不能把敌怪必需的重做全部归因于新增管理器。这是后续架构评估的前提，具体管理架构与 DOOM 兼容范围仍待确定。阶段 0 复用 Momoi 玩家实体验证移动的范围单独保留。

## 2. Compatibility Targets / 先区分兼容目标

| 目标 | 必须解决的问题 | 对实体管理的要求 |
|---|---|---|
| 读取地图与素材 | lump、资源覆盖、坐标、地图引用与出生信息 | 不要求使用 DOOM 的内存结构或 thinker 链表 |
| 地图按预期可玩 | 实体映射、体型与通行、钥匙/门/开关、传送、机关、死亡触发与通关条件 | 必须保留地图依赖的交互语义，并验证支持范围 |
| 原版行为精确兼容 | 逻辑频率、数值运算、随机数调用、遍历顺序、碰撞细节与状态动作 | 需要严格模拟及对照轨迹；通用 Godot 移动不能自动满足 |

以上是评估层次，不是已经批准的产品兼容等级。

经典二进制地图的 `THINGS` 记录只有 `x/y/angle/type/options`。引擎再以 `mobjinfo[i].doomednum` 查找类型，读取程序中的类型与状态定义生成物体；出生记录并不自带完整实体逻辑。

证据：[mapthing_t](E:/DOOMSourceCode/linuxdoom-1.10/doomdata.h:203)、[P_SpawnMapThing](E:/DOOMSourceCode/linuxdoom-1.10/p_mobj.c:708)、[类型映射](E:/DOOMSourceCode/linuxdoom-1.10/p_mobj.c:753)、[mobjinfo](E:/DOOMSourceCode/linuxdoom-1.10/info.c:1106)。

因此，采用相似的数据概念有助于建立映射，真正决定兼容性的仍是这些数据如何参与运行规则。扩展地图格式或脚本行为需要另外声明和实现支持范围，不能由“能读 WAD”推出。

兼容还超出实体系统：DOOM II `MAP07` 的相关 Boss 死亡会触发 tag 666/667 的地板行为。即使实体创建、移动与死亡全部正常，遗漏此类规则仍会改变地图进程。

证据：[A_BossDeath 地图与类型判断](E:/DOOMSourceCode/linuxdoom-1.10/p_enemy.c:1616)、[存活同类检查及地板触发](E:/DOOMSourceCode/linuxdoom-1.10/p_enemy.c:1692)。

## 3. Ownership / 建议的职责边界

| 部分 | 建议职责 | 避免的耦合 |
|---|---|---|
| 模式世界 / `EntityWorld` | 本局实体身份、创建/删除、玩家身体绑定、查询入口和调度所有权 | 不包办全部 AI、武器、动画或地图解析 |
| 实体定义 / `EntityDefinition` | 体型、基础属性、能力、行为与表现资源的共享配置 | 不把每个实例状态重复放入配置资源 |
| 玩家状态与控制器 | 选用角色、输入、装备与当前身体的关联；产生动作意图 | 不将 Momoi 场景节点路径作为通用实体接口 |
| 实体身体与行为 | 位置、速度、碰撞及所需行为；只有一个移动执行者 | 不让旧状态机、新控制器和管理器重复移动 |
| 地图空间与交互规则 | 地面/天花板、开口、通行、射线、触发线与 sector 更新 | 不把全部 linedef 固化为永久二维墙体 |
| 表现适配 | 精灵、动画、朝向、阴影、光环与音效 | 不以精灵偏移替代世界高度，不让动画帧率决定模拟 |

生命周期管理、模拟调度和空间查询可以由不同模块实现，不要求集中成一个巨型管理器。

借鉴 `player_t ↔ mobj_t` 的目的，是分开玩家身份与本次身体的生命周期。Momoi 可以是其中一种身体配置；死亡、重生、换角色后，控制身份不必跟随旧身体销毁。证据：[player_t](E:/DOOMSourceCode/linuxdoom-1.10/d_player.h:83)、[P_SpawnPlayer](E:/DOOMSourceCode/linuxdoom-1.10/p_mobj.c:642)。

门、平台和灯光应接入世界更新任务，不必伪装成角色身体。DOOM 的 thinker 也调度这些任务；地图基础结构并非全部属于 `mobj_t`。证据：[thinker 约定](E:/DOOMSourceCode/linuxdoom-1.10/p_tick.c:36)、[地图灯光任务](E:/DOOMSourceCode/linuxdoom-1.10/p_spec.h:124)。

## 4. Keep and Change / 哪些保留，哪些改造

| DOOM 设计或实现 | 对 ETNDOOM 的建议 |
|---|---|
| 统一创建、登记与移除入口 | 保留职责，便于跟踪本局归属和清理 |
| 玩家状态与世界身体分离 | 保留，避免把输入、身份与具体角色场景绑死 |
| 实例引用共享类型配置 | 保留；DOOM 类型号在导入边界映射到模组定义 |
| 更新集合、空间集合各有用途 | 保留；容器和索引按需求选择，不照搬三套侵入式链表 |
| 固定模拟步与明确执行顺序 | 保留设计目标；35 Hz 仅在选定的行为兼容目标需要时采用 |
| 延迟销毁 | 保留遍历安全的目标，同时明确何时停止交互、何时解除索引与释放 |
| 大结构体与兼任多个语义的字段 | 按需要拆分；追击目标、弹丸发射者、控制者分别表达 |
| 裸指针长期引用与结构体直接存档 | 改为可校验的引用和显式数据；池复用须识别不同生命期 |
| 状态表同时驱动行为和精灵 | 原版行为适配可保留动作时序；ETN 表现独立读取模拟状态 |
| 固定二维尺寸假设、全局碰撞临时变量 | 不作为通用契约；查询需显式输入和有效的候选覆盖规则 |

运行时实体 ID、地图源记录编号、类型定义 ID 是不同概念，建议明确区分。不要将 WAD 的 `type` 当作实例 ID，也不要将节点路径当作跨存档或网络的永久标识。槽位复用时可采用代数；阶段 0 没有池、存档和联机，不要求提前实现完整句柄系统。

ECS、全量对象池、多线程与批量弹丸系统均可后评估。是否需要它们应由实际实体负载与性能测量决定；目前没有可以支持性能承诺的运行结果。

## 5. Compatibility Costs / 不可忽略的兼容代价

### 5.1 Collision and body size / 体型与碰撞

当前 Momoi 根碰撞圆半径为 7、局部偏移 `(0,-6)`；DOOM 玩家定义的 `radius=16`、`height=56`。两者的空间判定也不等价：DOOM 普通物体相互阻挡使用 XY 轴向范围比较，不能因字段名为 radius 就将它视作精确圆碰撞。

证据：[Momoi 碰撞资源](E:/ETN_DOOM/scenes/player/momoi/momoi.tscn:33)、[Momoi 实体](E:/ETN_DOOM/scenes/player/momoi/momoi.tscn:260)、[MT_PLAYER 配置](E:/DOOMSourceCode/linuxdoom-1.10/info.c:1124)、[PIT_CheckThing](E:/DOOMSourceCode/linuxdoom-1.10/p_map.c:252)。

由此可推断，保持 Momoi 的原体型会改变某些间隙的通行结果；改用 DOOM 体型则会改变 Momoi 的操控与视觉贴合。尺寸、锚点与通行能力应显式配置并接受测试，不应因复用场景而被动决定。阶段 0 的选择也不得自动冻结后续兼容体型。

普通实体相互阻挡缺少完整的高度重叠检查，弹丸另有 Z 检查；“无限高阻挡”等属于规则选择，不是链表容器造成的必然限制。ETNDOOM 可以制定自己的高度规则，但相应地图行为差异必须承认和验证。

### 5.2 Scheduling / 时序

DOOM `P_RunThinkers` 按当前链表依次执行，回调中的新对象追加到链尾，有可能在同一 tic 得到更新。动作也可能立即造成伤害或状态变化。把它统一改成“全部决策 → 全部移动 → 帧末处理所有伤害和生成”会改变可观察顺序。

证据：[P_AddThinker](E:/DOOMSourceCode/linuxdoom-1.10/p_tick.c:65)、[P_RunThinkers](E:/DOOMSourceCode/linuxdoom-1.10/p_tick.c:101)、[状态进入动作](E:/DOOMSourceCode/linuxdoom-1.10/p_mobj.c:54)。

ETNDOOM 可以选择更清楚的更新顺序，但应将其记为本模式规则。若以后追求严格兼容，应逐项复现相关时序，不能把帧末命令队列当作天然兼容的“现代化”替代。

35 Hz 与原版随机表也是严格兼容的部分条件，而非充分条件；还需匹配运算和调用顺序。普通模式可选择自己的模拟频率，不能通过修改整个宿主项目的物理频率来顺带承诺兼容。

证据：[TICRATE](E:/DOOMSourceCode/linuxdoom-1.10/doomdef.h:122)、[定点数](E:/DOOMSourceCode/linuxdoom-1.10/m_fixed.h:35)、[P_Random](E:/DOOMSourceCode/linuxdoom-1.10/m_random.c:57)。

### 5.3 Godot and map rules / Godot 物理与地图规则

阶段 0 按现有约束使用真实 `CharacterBody2D.move_and_slide()` 与矩形静态边界，适合验证该阶段目标。后续 WAD 的双面线开口、台阶、天花板、动态 sector 和穿线触发需要专门验证，不应声称 Godot 平面碰撞已覆盖这些语义。

建议在第一次复杂通行实现前明确谁决定最终合法位置。Godot 可以作为阶段 0 的移动执行者；后续是否继续承担部分平面阻挡，要以空间规则测试决定。两个独立系统分别积分同一实体位置、再互相纠正，容易产生双重移动与不一致。

若未来严格复现 DOOM 的移动，应重新评估独立碰撞求解及模拟时钟的成本。隔离移动入口可以降低替换影响，但不能消除重做、地图回归和表现适配的成本。

证据：[阶段 0 移动要求](E:/ETN_DOOM/ETNDOOM/ModdingDocs/Stage0/STAGE_0_DEVELOPMENT_DETAIL.md:119)、[P_TryMove](E:/DOOMSourceCode/linuxdoom-1.10/p_map.c:451)。

### 5.4 Rules are world choices / 规则应按整局选择

如果需要 ETN 扩展规则与 DOOM 接近原版的规则，建议按整局选择经过测试的规则组合，包含调度、通行、地图交互和实体定义。不要承诺给某个实体打一个“DOOM”标签，就能与同场其它规则精确共存。

许多行为涉及实体双方和共享地图，例如钥匙开门、踩线触发、阻挡与伤害。组合是否成立需要一致的交互契约。初期只实现一套明确规则；确有需求再增加第二套，避免提前维护两份引擎。

## 6. Stage 0 and Next Steps / 当前应做到哪里

以下第 1–3 项按已确认的 D06 与阶段 0 范围执行；后续架构和兼容扩展仍为建议。功能实现须先满足阶段 0 的其余实施闸门：

1. D06 已确认由最小新逻辑接管 Momoi：继续加载 C02 指定原场景，在入树前处理原信号、玩法子树和组，以模组自有根脚本驱动同一个物理体；具体决策见 §6.1。接管路径仍需运行证明。
2. 阶段 0 仅完成一个玩家的输入、移动、碰撞与表现，按 D06 沿用基础输入、加减速与物理形状作为对照。新逻辑验证的是 ETNDOOM 的移动路径，不是原 `Player` 完整兼容。
3. 阶段 0 可只留一个清楚的移动入口，由一个物理回调驱动；不要求先建设完整实体注册表、调度器、AI、战斗、35 Hz 模拟或规则切换框架。
4. 后续契约阶段先明确 WAD 支持范围、体型、高度与通行判例，再确定实体与空间服务边界。保留原始 line/sector/type 等来源信息，避免转换时丢失将来实现交互所需的数据。
5. 到第一次跨实体交互时，再落实必要的身份、生命周期、查询和更新顺序；用玩家、一个为新地图与规则大幅重做或新设计的敌人、一种攻击逐步验证。阶段 5/7 按 §1.1 推进敌怪行为与刷怪调度，不设整体接管原版敌怪行为的迁移任务。
6. 以小地图分别测试门/钥匙、开关、台阶、传送、机关、死亡触发与出口；不支持项在加载或兼容报告中明确指出。通过单张矩形图不能宣称完整 WAD 兼容。

若用户后续把目标提升为原版 demo 同步或精确物理，应先暂停相应兼容承诺，评估是否采用更接近 DOOM 的模拟核心，并用原版轨迹对照。此处没有创建第二套运行时，也没有批准迁移全部实体。

### 6.1 D06 Decision / D06 已确认决策

用户于 2026-10-24 确认采用“实例化原 Momoi 场景，在入树前适配根逻辑和子树”。该决策结合 [ETN 原版实体管理](ETN_ENTITY_MANAGEMENT.md) 的调查与 §1.1 的敌怪重做前提：保留原实例的 `CharacterBody2D`、碰撞和必要外观资源，从 `Stats` 提取基础移动参数；以直接继承 `CharacterBody2D` 的模组自有根脚本取得移动与必要表现的执行权。具体范围、信号处理顺序、移动基线、朝向和验证要求见 [Momoi 分析 §8.3](STAGE_0_MOMOI_ANALYSIS.md#83-momoi-adaptation--沿用原场景的接管方案)。

该选择的收益是将后续地图与通行规则的接入点放在 ETNDOOM 自己的逻辑中，并避免为了一个纯移动测试维持原玩家的整套玩法依赖。敌怪已预期重做，后续无须以兼容其旧运行行为来约束新控制入口。

阶段 0 只落实一个由模组控制的玩家实体；完整实体注册、生命周期、查询和统一调度在实际需要跨实体交互时逐步建立。D06 已确定这条最小路径，全面实体管理架构、35 Hz、DOOM 精确行为和阶段 1 空间契约另行决定。沿用原物理形状和基础加减速参数，只作为本阶段的对照，不承诺原版玩家或 DOOM 完整兼容。
