### 3.1 V01 Decision and Projection / V01 决策与投影关系

V01 冻结的世界映射为：

```text
wad_x      → world_x
wad_y      → -world_z
wad_height → world_y
```

其中阶段 0.3 使用 `1 world unit = 1mu`，世界各轴单位一致，WAD 地图平面不做额外非均匀缩放；角色精灵保持竖直，不能随地面投影整体压扁或旋转。`pitch=45°` 是 ETN 本阶段的明确选择，覆盖 isodoom 当前默认的 `pitch=55°`，但保留其正交相机与轴向映射方式。

相机从 WAD 东南侧望向西北侧，屏幕上方为 WAD 西北、右方为 WAD 东北。Godot 相机 Euler 旋转为 `(-45°,45°,0°)`：pitch 表示向下俯角，不应直接作为正 X 旋转。

以 `u=wad_x`、`v=-wad_y` 为逻辑平面、`h=wad_height` 为竖直高度，§3.1 公式给出由固定 `Camera3D` 相机基底应产生的解析投影参照：

```text
projected_x = origin_x + (u - v) / √2
projected_y = origin_y + (u + v) / 2 - h / √2
```

等价的归一化投影参数为：

```text
a = 1 / √2 ≈ 0.7071
b = 1 / 2   = 0.5
c = 1 / √2 ≈ 0.7071
```

`projected` 是用于独立计算和对照的二维投影参照，不是再叠加到 3D 场景上的第二次变换；运行画面由 `Camera3D` 一次性投影 3D 表现坐标。WAD 正方形边长为 `L` 时，解析投影包围尺寸为宽 `√2·L`、高 `L`，因此菱形宽高比为 `√2:1`（约 `1.414:1`）。玩家平地脚底使用 `h=0`；墙面顶底高度来自各自 sector（V05），不据此冻结阶段 1 高度单位。

给定 `h`，令 `A=(projected_x-origin_x)/a`、`B=(projected_y-origin_y+c*h)/b`，可反求 `u=(A+B)/2`、`v=(B-A)/2`。鼠标反投影前须撤销相机/视口变换；未来多高度表面须另行选择命中地面。碰撞、导航与距离在经确认的逻辑空间中判断，不能用屏幕菱形的轴对齐包围盒充当可走范围。

### 3.2 V02 Decision and Coordinate Responsibilities / V02 坐标职责决策

V02 已决策：**逻辑空间是唯一权威坐标，投影和窗口显示都是只读表现层；物理判定不运行在投影平面或窗口像素中。** 所有需要位置、方向、距离、边界或高度的系统，先消费逻辑空间数据；表现层读取同一份逻辑状态后生成投影位置，不把显示结果写回逻辑状态。

#### 3.2.1 Runtime spaces and reference / 运行坐标与解析参照

| 空间 | 典型表示 | 职责 | 不得承担的职责 |
|---|---|---|---|
| WAD 源坐标 | `(wad_x, wad_y, wad_height)` | 地图文件顶点、出生点和原始高度的输入；由导入层转换一次 | 不直接作为运行时碰撞、导航、距离或窗口位置 |
| 逻辑空间 | `(u,v,h)` | 地图查询、实体状态、移动、碰撞、导航、出生距离、攻击距离和边界判断的唯一依据 | 不包含相机位置、正交相机 `size`、视口尺寸或窗口像素取整 |
| 表现世界 | `(world_x,world_y,world_z)=(u,h,v)` | 3D 表现几何的坐标；由 V01 正交 `Camera3D` 产生最终视图投影，用于地面、墙面、脚底与角色显示 | 不用于替代逻辑距离、形状半径、可走范围或物理法线；不承载 3D 物理 |
| 解析投影参照 | `(p_x,p_y)` | 按 V01 公式独立计算预期画面位置，供锚点、投影和测试断言对照 | 不作为 3D 实际渲染后的第二次投影，也不用于逻辑判定 |
| 窗口像素 | `(x_px,y_px)` | 经过相机与视口变换后的最终画面坐标；用于截图采样和未来鼠标反投影入口 | 不写回实体逻辑位置，也不作为地图边界或碰撞判据 |

逻辑已将 WAD Y 反号一次：`v=-wad_y`；因此 `world_z=-wad_y=v`。正向映射为 `(u,h,v)`，反向为 `(x,z,h)`。旧稿额外的 `-v` / `-z` 与 V01 轴向及解析公式冲突，已统一修正；旧写法与依据见历史附录 §C.2。

#### 3.2.2 Origin, units and axes / 原点、单位与轴向

- WAD 原点 `(wad_x, wad_y)=(0,0)` 映射到逻辑原点 `(u,v)=(0,0)`；当前阶段沿用 `u=wad_x`、`v=-wad_y`，单位保持 1:1。`h` 为独立竖直高度，正方向向上；阶段 0 玩家平地脚底固定使用 `h=0`，不借此冻结阶段 1 的高度单位。
- 逻辑原点在规范投影平面中对应 `P(0,0,0)=(origin_x,origin_y)`。`origin_x/y` 只是显式的投影平面锚点，不是相机中心、窗口中心或地图边界；测试可将其置为 `(0,0)`，运行时的显示平移必须通过明确配置传入，不能偷偷改写逻辑坐标。
- 在投影平面中，`u` 增大使位置向屏幕右下方向移动，`v` 增大使位置向屏幕左下方向移动，`h` 增大使位置向屏幕上方移动；这些方向由 §3.1 的固定公式产生，不通过旋转显示节点临时修正。
- 逻辑和投影计算保留浮点值，不在中间步骤取整。像素吸附或最终栅格化若由渲染配置启用，只能发生在显示末端，不能反向影响逻辑状态、碰撞或反投影结果。

#### 3.2.3 Transform order / 变换顺序

所有实现统一遵循以下单向链路：

```text
WAD source
  → logical (u, v, h)
  → presentation world (x, y, z) = (u, h, v)
  → orthographic Camera3D projection [fixed V01 yaw / pitch / projection basis]
  → viewport transform              [design viewport / stretch / window]
  → window pixels (x_px, y_px)
```

逻辑坐标、3D 表现坐标和窗口像素必须使用不同的变量和接口命名；不能把 `projected_x/y` 直接当作鼠标像素，也不能把窗口鼠标位置直接当作 `(u,v)`。相机跟随、正交相机 `size` 和窗口拉伸只改变显示结果，不改变逻辑位置或物理结果。实现应集中在一套正向/反向转换接口中，避免各实体、墙面和测试脚本各自复制不同公式；不得将 3D 表现节点或 `Camera3D` 变成第二套状态真源。

#### 3.2.4 Inverse and height precondition / 反投影与高度前提

窗口像素反投影必须严格按相反顺序执行：

```text
window pixels
  → inverse viewport transform
  → Camera3D ray
  → intersect a selected plane at known h
  → presentation world (x, h, z)
  → logical (u, v, h) = (x, z, h)
```

阶段 0 的反投影样例固定与 `h=0` 平面求交；未来存在多个高度表面时，必须先由命中规则选定平面，再将世界交点转回 `(u,v)`。未知高度时一条相机射线不能唯一确定逻辑点，不能用默认的精灵高度或上一帧高度静默代替平面选择。§3.1 的解析逆变换用于独立核对相机结果；V02 只冻结转换接口和前提，不因此加入鼠标瞄准玩法。

#### 3.2.5 Physics and state ownership / 物理与状态所有权

- 玩家根状态、碰撞形状中心、速度、地图边界和接触结果均以逻辑 `(u,v,h)` 表达；投影比例不得通过父节点 `scale`、`skew` 或屏幕菱形半径隐式改变物理形状。
- 角色脚底和精灵是表现锚点，读取逻辑脚底位置并投影到显示层；阴影位置接口也从该锚点派生，但 0.3 不渲染阴影。根节点、碰撞中心和可视脚底的偏移必须分别记录，不能用精灵包围盒反推碰撞。
- 相机位置、正交相机 `size` 或视口尺寸改变后，逻辑坐标、碰撞结果、导航距离和边界判定必须保持不变；只允许窗口像素位置发生变化。
- 屏幕菱形的轴对齐包围盒、截图像素边界和墙面贴图边缘都不能充当逻辑可走范围。`MapBounds` 等全局边界服务也不因 V02 变成新模式的物理来源。

V02 的纯变换验收至少覆盖逻辑原点、地图四角、中心、出生点、外侧点和非零高度样例；正投影再反投影后应在 `1e-5` 逻辑单位内回到原值。改变相机位置、缩放和窗口尺寸后，仍须通过同一组逻辑不变量；运行截图的像素容差另按 §5 的视觉验收记录。

### 3.3 V03 Decision: Input and Motion / V03 输入与移动决策

V03 已决策：**移动输入表达屏幕方向，经过 V01 的逆投影变为逻辑方向；全方向优先保持相同的逻辑速度长度；速度状态以逻辑空间向量保存，并用一个向量加速度上限更新。** 输入、速度、加速度都不在窗口像素空间计算，相机位置、正交相机 `size` 和视口尺寸不能改变移动结果。

#### 3.3.1 Screen input to logical direction / 屏幕输入转逻辑方向

输入二维基底采用 V01 投影平面方向：`screen_x` 向右为正，`screen_y` 向下为正；它表示方向而非窗口像素位移。先将输入拆成单位屏幕方向与强度：数字方向输入的非零斜向向量归一化（如 `(1,1) → (1/√2,1/√2)`），强度为 `1`；模拟摇杆向量长度钳制到 `[0,1]` 作为强度，非零向量方向归一化。以下公式中的 `screen_x/y` 是单位方向分量，不含强度。再用 V01 平面逆投影的线性部分转换：

```text
logical_u_raw = screen_x / √2 + screen_y
logical_v_raw = screen_y - screen_x / √2
logical_direction = normalize((logical_u_raw, logical_v_raw))
```

最终再归一化逻辑方向，是为了令所有方向的满输入目标逻辑速度长度一致；不能直接把未经归一化的逆投影向量乘 `525mu/s`，否则屏幕上下左右会有不同逻辑速度。模拟输入的强度乘到目标速度上，不得把摇杆的半幅输入误当满速。零输入没有目标方向，目标速度为零。以上只定义移动输入，不增加鼠标瞄准。

#### 3.3.2 Speed, acceleration and unit conversion / 速度、加速度与单位换算

用户指定 DOOM `map units`（`mu`）为基本长度：满输入稳态最大逻辑速度 `525mu/s`，统一向量加速度上限 `1720mu/s²`。MAP01 测试图以 `1024mu` 边长作为场景尺度参照；满速约为每秒 `0.5137` 个边长，静止加速到满速约需 `0.3052s`，恒定直线加速段约走 `80.1mu`。

```text
max_speed = 525mu/s
acceleration = 1720mu/s²
target_velocity = logical_direction * max_speed * input_strength
velocity = velocity.move_toward(target_velocity, acceleration * delta)
```

`1 logical unit = 1mu` 是地图/逻辑坐标的正式长度约定，不由相机 `zoom`、窗口缩放或单张截图改变。`525mu/s` 与 `1720mu/s²` 同时也是 `525 logical units/s` 与 `1720 logical units/s²`；实现、测试和后续文档可直接使用 `mu` 标注逻辑长度、速度、加速度和距离。

单位依据：2026-10-26 的 Stage0.2 固定 `60Hz` 测算支持 `1:1`，用户已据此确认逻辑单位直接使用 `mu`。逐帧轨迹、`201` 帧接触结果及离散积分口径统一见[实施记录 §3.1](STAGE_0_IMPLEMENTATION.md#31-unit-measurement--单位换算实测2026-10-26)，本轮不重跑。

既有 0.1/0.2 原型的 `155` 逻辑单位/秒、`SPEED_TIME=0.2s` 和逐轴加速属于已验收的旧基线；V03 不回写或重新解释旧证据。未来 V03 实现以本节 DOOM `mu` 参数为准，因 `1 logical unit = 1mu` 可直接得到运行值。

起步、减速与反向共用一个向量加速度上限，不为起步、松键减速和反向输入另设不同响应参数。由指定数值可得：从静止达到 `525mu/s` 或满速制动到静止均约 `525/1720 = 0.3052s`；从一个方向满速反向到相反方向满速约 `2×525/1720 = 0.6105s`。反向所需时间更长是速度向量需跨越 `1050mu/s` 的结果，不是另一个调节参数。向量 `move_toward` 替代原阶段 0 的逐轴加速，避免逆投影后各逻辑分量各自接近目标造成方向相关的响应。

“相同逻辑速度”是逻辑平面欧氏长度相同，不承诺投影后画面各方向每秒像素位移相同；方向投影长度不同是 V01 几何的结果。若未来要改为屏幕等速，必须重新裁定 V03，不能通过相机缩放偷偷补偿。

### 3.4 V04 Decision: Logical Collision and Presentation Anchors / V04 逻辑碰撞与表现锚点决策

- 平地碰撞使用逻辑轴对齐 `RectangleShape2D(size=Vector2(32,32))`，完整尺寸 `32×32mu`；禁止用带碰撞体父节点的 `scale` / `skew` 伪造投影。
- 实体根点、矩形中心、逻辑脚底是分别命名的接口，三者平面偏移均为 `(0,0)mu`；矩形围绕根点对称，脚底 `h=0`。精灵像素脚底通过显示锚点对齐，竖直几何见 V06。
- 阴影位置接口可由逻辑脚底派生，但 0.3 不实例化或绘制阴影。精灵包围盒、显示高度及窗口像素都不参与 2D 碰撞判定。
- 验收覆盖四边、四角、沿边滑动、离墙与斜向接触；逻辑断言使用上述矩形，视觉断言使用接触几何的 V01 投影。相机与视口变化不得改变接触结果。
- 只在 0.3 的 Momoi 适配实例中替换形状，不修改共享原场景。0.1/0.2 保留根圆 `radius=7`、偏移 `(0,-6)` 及旧适配校验（`etndoom_mod/stage0/stage0.gd:88-90`）。

### 3.5 V05 Decision: Floor and Walls / V05 地面与墙面决策

#### 3.5.1 Geometry, fields and sampling / 几何、字段与采样

- 当前 `MAP01.wad` 经原始 lump 核对为单 sector：地面高度 `0mu`、天花板高度 `128mu`、地面 flat `FLOOR0_1`、顶面 flat `CEIL1_1`；四条 linedef 各有一个 sidedef，唯一 wall slot 为 `STARTAN2` middle，upper/lower 为 `-`。四个 sidedef 的水平/竖直纹理偏移均为 0；四条 linedef 的 flags 均为 `1`（`ML_BLOCKING`），不含 `ML_DONTPEGBOTTOM`。证据：`etndoom_mod/wad/MAP01.wad`；格式读取位置见 `etndoom_mod/stage0/stage0_wad.gd:102-136`。
- **已决策：地面 UV**：地面纹理以 WAD/逻辑平面坐标 `(u,v)=(wad_x,-wad_y)` 采样；UV 不随地面投影预先压成菱形。
- **已决策：采样参数**：地面与墙面以源纹理原生像素密度采样，即 `1 texel/mu`；使用 nearest 过滤，启用 mipmap 以减轻斜视地面在缩小时的闪烁；不启用各向异性过滤。纹理超出边界时按源图实际宽/高 repeat，而非套用 isodoom 的 vanilla 列/行特殊回绕。当前 `FLOOR0_1` 为 `64×64`，重复周期为 `64mu`；`STARTAN2` 为 `128×128`，重复周期为 `128mu`。这只定义纹理采样，不改变 WAD 几何、逻辑单位或地图尺寸。
- **已决策：墙体几何范围**：阶段 0 只绘制 WAD linedef 所代表的墙面本身；本阶段不在墙边/角生成额外延展、端部闭合、墙厚或顶面，不绘制常规 sector ceiling。`MAP01.wad` 单面墙表面的有效竖直区间来自其 front sector 的 floor `0mu` 至 ceiling `128mu`，不是在该区间外补长墙体；此渲染范围不成为玩家通行高度规则。
- **已决策：WAD 贴图字段派生**：Front/Back 各自引用一个 sidedef；每个 sidedef 的 `upper/middle/lower texture`、`textureoffset`、`rowoffset` 和 `sector index` 是该面的全部贴图输入，统一 offset 同时作用于该 sidedef 的三个纹理槽。linedef 的 `Double Sided`、`Upper Unpegged`、`Lower Unpegged` 分别按 vanilla Doom 的 `ML_TWOSIDED`、`ML_DONTPEGTOP`、`ML_DONTPEGBOTTOM` 解释；不添加 WAD 没有的独立 U/V、旋转、缩放或 skew 参数。
- **已决策：坐标派生**：U 从该 sidedef 的局部起点沿局部终点方向累加距离，并加该 sidedef 的 `textureoffset`；Front 使用 linedef `V1→V2`，Back 使用反向 `V2→V1`。V 使用 `rowoffset` 和 vanilla Doom 的 section pegging 规则；0.3 当前 one-sided middle 的具体规则为：在 `rowoffset=0` 时，未设置 `Lower Unpegged` 则 texture row 0 锚定 front sector ceiling，设置时 texture bottom 锚定 front sector floor；随后叠加 `rowoffset`。U/V 超出纹理边界按纹理实际尺寸 repeat。
- **阶段 0 的双面范围**：`MAP01_BackWall.wad`/`MAP01_FrontWall.wad` 中的双面 `MIDGRATE` 与 sector 高差、透明孔洞及自然深度遮挡属于本阶段实现和回归承诺；夹具之外的 upper/lower/masked-middle 组合、动态 sector 高度及完整 wall-section 扩展留给未来 sector 阶段，不是 V05 的待决参数。

`repeat` 是纹理采样规则，不扩大 section 几何。双面 masked middle 按两侧开口及单次纹理高度裁切，不因 sampler repeat 而纵向铺满整墙；透明孔洞按 V06 丢弃。完整 section/pegging 推导参考[sector 墙体说明 §1–§2](ISODOOM_SECTOR_WALL_RENDERING_REFERENCE.md)及 `E:/isodoom/src/Map/WallSections.cs:315`；只实现五张夹具实际需要的子集。

### 3.6 V06 Decision: Occlusion and Sprites / V06 遮挡与精灵决策

- **已决策的核心机制**：平面移动、碰撞、导航和距离留在 2D `(u,v)`；V02 的独立高度标量 `h` 仍由逻辑数据提供，0.3 不引入 3D 物理。地面、墙体和角色由同一 3D 表现世界与正交 `Camera3D` 绘制。墙体和角色材质都参与深度测试，按相机空间的逐像素深度决定可见片段，因此近侧墙自然遮住角色，远侧墙位于角色后。透明 `MIDGRATE` 孔洞必须丢弃片元并且不写深度，不能把透明纹理矩形当作实体遮挡。
- 阶段 0.3 只验证自然深度遮挡；明确不实现、不配置、不验收半径 `cutaway`、透明 `dither`、角色墙面拉近 `wall pull`、`upright hiding`，以及之后为提高可读性提出的同类策略。若自然遮挡导致边缘测试截图看不见角色，仍须使用逻辑位置/碰撞结果判定，不能临时加入可读性例外、修改物理或改变墙高。
- **阶段 0 阴影范围**：0.3 不创建、不渲染或验收阴影。V04 的逻辑脚底锚点仍是后续生成阴影的位置来源；阴影几何、透明度和深度关系均留给后续开发，不构成 V06 的阶段 0 未决项。
- **角色精灵实施基线（2026-10-30 人工反馈修正）**：Momoi 使用竖直 billboard，绕世界竖直轴朝向相机；每帧主体在 `alpha>=0.5` 下的可见包围高度为 `56mu`，主体底边中心对齐逻辑脚底锚点。`56mu` 不包含光环或透明留白；以主体可见高度确定每像素 mu 比例，主体和光环共同等比缩放，保留原 `HaloRoot` 相对位置、光环旋转和缩放，合成图总高允许超过 `56mu`。透明像素按 `alpha<0.5` 丢弃，保留像素参与正常深度测试/写入，碰撞尺寸保持独立。HTest 中穿入 50mu sector 后须看见主体像素，不能用光环代替。用户已确认修正后的高度正常。后续 billboard 模式和角色绑定高度不扩展为本阶段验收要求。
  - SUPERSEDED: 2026-10-30，旧实现把含光环合成图整体缩到 56mu，导致待机主体实际约 35.9mu（用户视觉估计约 33mu）；旧“图像/帧自身范围”不能再理解为包含光环的整体高度。
- **自然投影缩短（2026-10-30，user + test）**：竖直 billboard 的世界几何按原素材等比缩放，经过 pitch=45° 的正交相机后，屏幕纵向每 texel 长度是横向的 `cos45=1/√2≈0.7071`；正视素材的屏幕宽高比因此增加 `√2` 倍。这是视线与竖直平面的夹角产生的投影缩短，非贴图被错误缩放，也非透视近大远小。“不能随地面压扁”禁止对角色叠加地面变换，不取消相机对竖直几何的自然投影。用户明确该因素可忽略；保留竖直 billboard，不做纵向拉伸补偿，不切换为完全面向相机。原素材、世界等比与最终截图需分别验证。
- **墙体遮挡范围**：墙体按实际 3D 几何与相机空间深度测试角色精灵的所有垂直区域，包括头部；不得为保证头部可见而跳过墙体深度测试或修改角色深度。角色被完全遮住是允许的，逻辑位置和碰撞仍独立判定。
- **已决策的深度比较与双面 linedef 规则**：墙体与角色使用 Godot 默认深度测试，不设置 `depth_test_disabled`；同一像素由相机空间更近的片元胜出，不依赖绘制顺序、材质优先级或 `z_index`。不透明墙面和角色保留像素写入深度，透明像素在深度写入前 discard。双面 linedef 的两侧各按自身 sidedef 建立几何与 UV；固定相机下通过面朝向/背面剔除只让朝相机的一面输出片元，避免同一平面的两侧同时参与深度竞争。相同深度不作为排序规则。
- **z-fighting 处理边界**：DOOM WAD 的墙体边缘与地面边缘没有重复覆盖区域，因此阶段 0 不对这类交界预先增加接缝几何、全局 polygon offset、固定深度偏移或其他防护。若实际画面/测试发现 z-fighting，再基于复现结果进入下一步调试；当前不预设修复方案。
- 验收参照：中心时角色无遮挡；远侧边界处墙在角色后；近侧边界处由深度决定墙/角色遮挡，角色可部分或全部不可见；透明孔洞显示后方内容（角色透明边缘效果须人工验收）；四角不得出现错误顶点/面选择造成的墙缝、排序翻转、深度闪烁或透明片元遮挡；V05 排除的厚度/顶面缺失不算漏面，不得为截图补造几何。逻辑碰撞结果始终独立于视觉遮挡，阶段 0 不检查阴影。

### 3.7 V07 Decision: Camera and Framing / V07 相机与取景决策

- 测试场景只持有一台独立、活动的正交 `Camera3D`，通过确定的跟随/overview 两套相机参数切换；不并行启用第二台相机。V01 投影公式只作为解析参照，不在 3D 结果上叠加全局菱形旋转或额外缩放。
- 游戏跟随模式每帧硬跟随逻辑脚底锚点 `(u,v,0)` 映射后的 3D 位置 `(u,0,v)`；不启用平滑、死区、预测、准星前导、震屏或演出偏移。相机的取景中心可相对脚底沿世界 `+Y` 固定偏置 `28mu`，对应 `56mu` 主体高度的一半，使相机中心瞄准主体几何中心；偏置只改变相机取景，不改脚底锚点、根点或逻辑位置。
- 游戏跟随模式的 `Camera3D.size` 是可配置取景参数，允许值为 `640, 650, …, 1600mu`，即范围 `640..1600mu`、调整步长 `10mu`。相机尺寸只改变可见范围；固定回归视口为 `1600×900px`，视口比例使用固定 16:9 设计画面，不把像素尺寸换算回逻辑坐标。每份回归元数据记录实际 `size` 与固定取景偏置；首个实机视觉校准后再冻结常用游戏视野值。
- 0.1/0.2 的 `Camera2D`、`zoom=(1,1)` 与旧取景约束只属于已验收的旧基线；不能用它们的 2D 画布排序替代 0.3 的 3D 深度缓冲。
- 整图证据切换到同一 `Camera3D` 的 overview 取景配置，以当前 WAD 的全部投影几何（地面四角、墙面顶边及需要展示时的出生角色可视范围）计算相机平面包围框；等比 fit，所有内容必须完整落在视口内，并尽量让内容边缘距窗口边缘约窗口尺寸的 `10%`。该比例是取景目标而非硬性等式；受内容与窗口宽高比不同影响，留白可不对称，不得拉伸几何来填满画面。基线 `MAP01.wad` 在 `1600×900px` 视口下的 overview `size` 约为 `1400mu`（按约 10% 上下边距估算，再向上取整到 `10mu`）；其他 WAD 按自身包围框同法计算。Overview 不改变投影节点 scale、UV、逻辑坐标或碰撞；中心/边/角操作截图仍使用跟随视角。

上述 overview `size` 估算采用**竖直可见高度**口径；实现应显式设置 `Camera3D.KEEP_HEIGHT` 并记录在元数据中，避免默认宽高锁定方式使 `1400mu` 估算失效。约 `1400mu` 是预估值，不代替最终几何包围框计算；游戏常用 `size`、实际偏置及两套 near/far 在实机校准后写入实施记录。

#### 3.7.1 Depth range / 深度范围

用最终测试相机变换计算全部需显示几何的相机空间深度 `d=-view_z`（相机前方为正）范围 `d_min..d_max`，包围范围包含各夹具实际地面/墙面几何（当前最高墙面 `128mu`）、主体 `56mu` 加光环的各帧完整可视几何及阶段 0 允许测试的角色移动范围。取 `margin = max(8mu, 0.02 × (d_max - d_min))`，并设 `near = max(0.1mu, d_min - margin)`、`far = d_max + margin`；若 `d_min - margin <= 0.1mu`，调整相机位置/取景使最近几何在 near plane 之外。游戏跟随模式须覆盖整个允许的相机跟随范围，overview 模式须覆盖整张当前地图；两种取景配置分别计算数值。使用覆盖所需范围的最窄 near/far 区间。计算规则已确认，具体数值在实现时按最终相机变换代入。

### 3.8 V08 Decision: Entry and Regression / V08 入口与回归决策

- 新模式选择只增加唯一入口 `--stage0=0.3`；`--stage0` 重复、混合或无值仍失败。V08 验收命令固定带上 `--stage0-collision=on`，仅允许 0.3 使用该开关；省略时默认解析值也是 `on`。碰撞参数同样拒绝重复、无值或非法值；非法请求记录原因，不切入测试场景，继续正常启动。`--stage0-collision=off` 不属于本轮测试项，不能作为通过依据；与 0.1/0.2 混用的碰撞参数应拒绝并继续正常启动。

- `1 logical unit = 1mu` 已确认；V01 公式的系数也已固定。无需另设或等待 `k`。验收中的 `Camera3D.size` 是显示范围参数，不是逻辑单位换算系数。

## 5. Acceptance / 验收设计

继续遵循 `ETNDOOM/MOD_TESTING.md` 的用户目录隔离、真实 Mod 安装/重启/entry、完整截图与像素校验要求，并补充：

1. **独立几何参照**：测试从 WAD 顶点与冻结参数独立计算四角、边中点、出生点投影，比较运行时及截图。不能直接调用待测函数生成全部期望，避免错误自洽。
2. **正反变换与逻辑不变**：覆盖原点、四角、中心、外侧点及非零高度的纯变换样例；使用 `1e-5mu` 正反变换容差，核对地图尺寸、出生点没有被显示参数改写。非零高度函数样例不增加运行地形。
3. **完整视觉证据**：固定窗口与明确的整图取景，取景须覆盖完整菱形、墙面和 Momoi 所在几何范围；仍允许墙自然遮住角色，不能为使角色可见而改深度或墙高；另保留游戏取景的中心、四边、四角状态，核对墙面、纹理、脚底和遮挡。
4. **像素参照**：保留同一 IWAD 的独立解码素材校验；增加投影后地面/墙面采样或独立参考渲染，明确 `1 texel/mu`、nearest、mipmap、按源纹理尺寸 repeat、相机与视口；墙面 UV 必须由 sidedef/linedef/sector/pegging 输入推导并记录，不能添加独立 U/V 或旋转控制。背景动画/glow 掩码不能遮掉主要几何、墙面或角色判据。几何锚点最多允许 `1px` 量化误差；未缩放解码素材逐像素核对，投影后的 mipmap 采样另记录期望层级/采样条件，不能直接拿源 texel 作错误的一一比较。
5. **物理对齐**：只在 `--stage0-collision=on` 下按 V04 的 `32×32mu` 逻辑矩形核对四边、四角、沿边、离墙与斜向移动。根点、碰撞矩形中心、逻辑脚底分开断言；视觉接触核对逻辑接触的投影，不能用角色根点或精灵包围盒替代碰撞判据。
6. **相机与方向**：改变 `Camera3D.size`/位置或视口尺寸后逻辑移动和接触不变；覆盖屏幕八方向到逻辑方向的独立参照、斜向归一化、逻辑速度长度、输入强度、起步/减速/反向响应及角色不随地面变形。长度、速度和加速度期望直接以已冻结的 `mu` 与 `1 logical unit = 1mu` 计算；相机 `size` 只影响显示范围。
