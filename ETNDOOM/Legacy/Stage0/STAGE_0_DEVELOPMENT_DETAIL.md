## 2. Scope / 阶段边界

### 2.1 Included / 必须包含

- 通过开发者命令行进入阶段 0 测试场景。
- 从 `MAP01.wad` 读取阶段 0 的矩形平地图。
- 显示地图素材，并把地图原点、尺寸、角色脚底锚点和相机位置固定为可检查状态。
- 按 D05 复用并启用全局泛光和场外滚动背景；背景由上层 WAD 地面遮盖场内，覆盖范围按测试视野适配。
- 实例化一个固定测试角色，只允许移动和观察地图。
- 0.1：场景几何与玩家根形状不启用碰撞，角色可越过与地图显示对齐的逻辑边界。
- 0.2：沿用同一份地图数据、素材与固定角色配置，启用玩家根形状和墙体 mask，并增加矩形边界的真实静态碰撞。两模式分别启动，不要求在同一进程中切换。
- 0.3：使用 V01–V07 的侧方正交视角与逻辑 2D/3D 表现；V08 验收固定使用 `--stage0-collision=on`。
- 自动回归检查加载、实体数量、禁用项、碰撞状态、投影、遮挡、边界行为和完整视口像素；0.1/0.2 不因 V08 决策再次运行。
- 人工运行检查素材位置、角色显示、边缘越界、四边碰撞、四角碰撞和沿边移动。

### 2.2 Excluded / 明确不包含

- 高台、楼梯、悬崖、空洞、地面高度和伪 3D 高度运动。
- 导航、敌人、突袭、刷怪、战斗、武器、技能、拾取和伤害。
- 完整 `ModeSession`、正式 `MapCatalog`、正式 `MapLoader`、正式 `MapDefinition` 和面向地图内容的 ZIP 导入功能。D04 仍须使用现有 SDK 的 Mod ZIP/PCK 构建与安装流程，见 §6.2；两种 ZIP 用途不得混淆。
- 原版回合流程、升级页、胜负、重开、退出清理和存档。
- 特效容器、伤害跳字、光照系统和场景 HUD；`ChipHud` 留待后续加入并修改，不在阶段 0 接入。
- 通过坐标钳制、边界传送或 `MapBounds` 回位模拟碰撞。
- 把阶段 0 的 WAD 原型读取方式或临时内部字段直接承诺为阶段 1 的正式地图格式。

## 3. Runtime Isolation / 运行时隔离要求

### 3.1 Entry and scene / 入口与场景

阶段 0 确定使用独立测试 Mod 作为开发者入口，由其 `entry` 读取 `OS.get_cmdline_user_args()`，通过 `--stage0=0.1`、`--stage0=0.2` 或 `--stage0=0.3` 选择测试模式。0.3 的 V08 验收命令固定为 `--stage0=0.3 --stage0-collision=on`；`off` 不列入本轮测试项。该入口不依赖 COOP Mod、不添加主菜单按钮、不修改正常选角流程；不把独立调试脚本或 `ExtensionHooks.change_scene_gate` 作为并列入口方案。

测试入口至少需要能够：

1. 判断当前命令行是否请求阶段 0。
2. 加载或实例化阶段 0 测试场景。
3. 选择 `0.1`、`0.2` 或 `0.3` 碰撞模式；0.3 的验收状态固定为 `on`。
4. 输出明确的阶段、地图 ID、角色资源和碰撞状态日志。
5. 在人工运行时保持窗口可操作，并允许通过输入移动角色。

阶段 0 不要求从测试场景返回原版菜单。若入口采用场景接管，必须在文档和日志中明确这是一次性开发测试路径，不能宣称已经完成模式生命周期。

### 3.1.1 Mod entry bootstrap / 测试 Mod 启动流程

以下流程为 D04 已确认的实现约束；入口已实现为 `res://mods/etndoom_stage0/entry/stage0_entry.gd`，隔离安装、重启挂载与参数矩阵均已验证，详见实施记录。

1. 测试 Mod 使用自己的 `mod.json` 和 PCK，场景与脚本资源归于 `res://mods/<mod_id>/`。入口相对路径约定为 `entry/stage0_entry.gd`，manifest 的 `entry` 指向 `res://mods/<mod_id>/entry/stage0_entry.gd`；脚本继承 `Node`。`<mod_id>` 是实施时使用的占位符，不表示已有该名称的 Mod 或目录。
2. 安装并启用测试 Mod 后必须重启。启动时 `ModManager` 扫描 Mod 目录及启用状态、挂载启用的 PCK、扫描内容并加载存档，再延迟运行 `_run_entry_scripts()`（`script/mod_manager.gd:89-105,203-243,255-263`）。entry 只在 Mod 已启用且挂载成功、入口资源存在且可加载、`api_version` 不高于本体支持版本时实例化。
3. entry 被添加到 autoload `ModManager` 下，名称为 `ModEntry_<mod_id>`，其 `_ready()` 因此可处理本次启动参数；它不属于当前主场景，切换主场景时仍存活（`script/mod_manager.gd:1059-1079`）。这只是 Mod 启动入口，不等于进入了阶段 0。
4. entry 通过 `OS.get_cmdline_user_args()` 解析参数，按下表决定是否启动测试；其它 Mod 的用户参数不由本入口处理。仅在有效请求下加载测试场景，普通启动不初始化阶段 0 角色、地图或玩法钩子。
5. 有效请求下，从 entry 延迟执行场景切换，通过 `SceneTree` 的场景切换接口进入阶段 0 测试场景，并将阶段选择交给测试场景初始化。该入口不经过 `GameEvents.change_scene()` 的原版玩家生成和首回合初始化，也不使用 `ExtensionHooks.change_scene_gate`。后者只拦截经过 `GameEvents.change_scene()` 的请求，无法自行触发启动（`script/GameEvents.gd:194-215`、`script/extension_hooks.gd:12`）。场景结构与角色隔离继续受 D05、D06、D07 约束。
6. entry 与测试场景分别输出启动、参数解析及实际加载结果。场景确认就绪后，日志至少包含阶段、地图 ID、地图尺寸、固定角色资源路径和 `collision_enabled`。资源加载或场景切换失败须记录原因，不能先报告测试成功；人工运行成功后保持窗口可操作，按 C04 作为一次性测试进程使用。

| 用户参数 | entry 行为 |
|---|---|
| 没有阶段 0 参数 | 直接返回，继续正常启动，不接管场景或注册阶段 0 钩子 |
| 恰好一个 `--stage0=0.1` | 进入阶段 0.1，测试场景使用 `collision_enabled=false` |
| 恰好一个 `--stage0=0.2` | 进入阶段 0.2，测试场景使用 `collision_enabled=true`；属于既有历史基线，不纳入本轮 V08 重跑 |
| 恰好一个 `--stage0=0.3 --stage0-collision=on` | 进入阶段 0.3，测试场景使用 `collision_enabled=true`；这是本轮唯一 V08 验收入口 |
| `--stage0=0.3` 未带碰撞参数 | 解析默认值 `on`；人工/自动验收仍应显式传入 `--stage0-collision=on` |
| `--stage0-collision=off` 或碰撞参数与 0.1/0.2 混用 | 不属于本轮测试项；实现若保留诊断解析，不得据此宣称 V08 通过 |
| `--stage0`、空值或其它阶段值 | 输出明确的参数错误，不切换测试场景，继续正常启动 |
| 重复出现阶段 0 参数，即使值相同 | 输出重复参数错误，不静默选取其中一个，不切换测试场景 |

直接切换场景不会移除本体 autoload 或其它 Mod；因此它本身不保证 `MapBounds` 和玩法信号已隔离，仍须按 §3.2–3.3 核对。entry 执行前已经调用 `Game.load_playerdata()`，所以自动回归必须在启动进程前完成用户目录隔离，不能等 entry 执行后再隔离（§6.1）。

### 3.1.2 Scene composition / 场景组成

D05 确认带入以下 10 个节点及必要资源：根 `Node2D`、`YSort`、`YSort/PlayerRoot`、`BackLayer`、`FloorLayer`、`BattleRoom`、`Control`、`Control/ColorRect`、`Control/TextureRect`、`WorldEnvironment`。此数量是主场景复用清单，不包含另行创建的 WAD 表现、Momoi、独立相机或 0.2 碰撞节点。

- 按[节点清单 §2–§4](STAGE_0_NODE_REUSE_CANDIDATES.md) 新建容器或复用资源，不实例化整张 `main.tscn`，不带 `main.gd`、原版地图几何、回合管理器及玩法容器。
- `BattleRoom` 不保留原坐标 `(704,448)`；地图定位与玩家出生点分别按 WAD 表达，不默认保留 `"CenterPosition"` 等原玩法组。`BackLayer` 与 `FloorLayer` 不重复绘制同一份 WAD 地面。
- `WorldEnvironment` 复用并启用 glow；glow 不等于实体描边，也不要求引入光照节点。
- `Control` 及两个子节点承载纯色底与场外滚动背景，由上层不透明 WAD 地面遮盖场内；不带入原版静态渐变和 `MapTest2`。背景须适配相机与 0.1 越界观察范围，不能假设原版有限矩形足够。
- 不引入场景 HUD 或额外调试 HUD；日志承担测试状态输出。`ChipHud` 阶段 0 不引入，后续会加入并修改。现有 autoload 与叠层按节点清单 §5 核对，不重复实例化。

### 3.2 MapBounds isolation / `MapBounds` 隔离

原版 `MapBounds` 在 `_ready()` 中订阅 `GameEvents.global_time_count`，之后按信号检查组 `"Player"` 中的实体；只关闭 `_process` 不能使其停止工作（`script/map_bounds.gd:35-76`）。因此阶段 0.1 和 0.2 都必须满足：

- `MapBounds` 不得处理阶段 0 测试角色。
- 不得依赖 `MapBounds.nearest_inside()`、坐标钳制或越界传送完成验收。
- 自动测试应能区分“角色因真实 `StaticBody2D` 停止”和“角色被原版边界逻辑拉回”。
- 按 D06，在入树前移除测试角色的 `"Player"` 等原版玩法组资格，由测试场景直接保存引用；不修改全局 `MapBounds`。实现时仍须核对保留节点不会重新加入原组。

### 3.3 Player isolation / 角色隔离

测试角色只保留必要外观与平面移动。以下按已确认 D06 的“入树前移除”执行，不再并列保留隐藏节点、关闭处理或仅禁用射击的替代方案。

| 原版部分 | 阶段 0 处理 |
|---|---|
| `Stats` | 提取并校验基础移动参数后移除；新根显式接收所需数值。 |
| `StateMachine`、`Gun`、`Kick`、跳跃与受击 Timer | 入树前移除；新根自行更新速度及待机/跑步表现，不保留攻击或跳跃输入路径。 |
| `MomoiPS`、`PlayerBuffManager`、`HealthComponent`、`HurtBox`、`PickBox`、`T_HP_Count` | 入树前移除，不注册技能、战斗、拾取、死亡或回合回调。 |
| `GameUI`、暂停 UI、原受击/踢击 `AnimationPlayer`、玩法音效及烟尘 | 不带入活动子树；不能以保留场景结构为由运行隐藏 UI 或保留玩法订阅。 |
| 原版 `Camera2D` 及附属黑幕/动画子树 | 入树前移除；测试场景独立创建相机，见 §3.3.2。 |

### 3.3.1 D06 Decision / D06 已确认方案

- 先实例化但不入树，读取并校验基础移动参数、保存必要外观与碰撞引用；在更换根脚本前清理指向旧根方法的场景信号连接，再移除并释放原状态机及玩法子树。不能只调用 `queue_free()` 后立即把仍带旧组件的根节点入树。`Stats` 提取数值后移除；更换脚本时显式传入参数与引用，不假设旧脚本字段自动保留。缺失节点或参数不合法时报出适配失败，不挂载半成品。

验收对象为“复用 Momoi 实体与基础配置的 ETNDOOM 移动路径”。运行时须证明原玩法回调未激活、每物理 tick 只有一次移动、0.1 可越界、0.2 真实阻挡与滑动；基础参数相同不代表原版 `Player` 完整兼容或 DOOM 物理兼容。入树前适配避免的是旧 `_ready()`/活动树回调；`instantiate()` 仍可能执行 `_init()` 和导出属性赋值，应按 Momoi 分析 §8.3 核对。

相机所有权与角色实体分离：测试场景直接持有两者，角色子树的替换不应连带替换测试相机。原版相机的平滑、准星前导、震屏与演出机制仅供分析参考，见[历史附录 B.2](STAGE_0_DECISION_HISTORY.md#b2-original-camera--原版相机行为分析)及 §9；不构成阶段 0 的行为要求。

### 3.3.3 D08 Edge crossing standard / D08 越界判定标准

用户于 2026-10-24 确认：**D08 由 D01、D02、D03、D06 共同收束**。D01 提供原型地图，D02 定义坐标和显示映射，D03 确定逻辑矩形及其派生碰撞，D06 确定玩家实体和实际根碰撞形状。D07 负责相机观察，不是 D08 的逻辑前置；D09 是独立的自动回归要求，完整截图与像素校验见 §1、§4.3、§5.3、§6.1。

- **地图边界**：以读取并校验后的 WAD 矩形范围为唯一几何真源，按 D02 映射得到 Godot 世界坐标中的四条边界线。地图外判定采用闭矩形：边界线本身不算地图外；对参考点 `p`，只有 `p.x < min_x`、`p.x > max_x`、`p.y < min_y`、`p.y > max_y` 中任一条件成立才算越界。当前测试图的映射范围为 x `[-640,384]`、y `[-512,512]`，数值仍由地图读取，不能写成第二套场景几何。
- **视觉对齐**：地面覆盖范围与逻辑矩形对齐；“越过边缘”指越过该逻辑边界线。`STARTAN2` 调试墙带的宽度或外沿、纹理有效像素或空白边、场外滚动背景的覆盖范围都不改变边界位置；显示与数据不符时修正显示映射。
- **0.1 判定点**：以阶段 0 玩家 `CharacterBody2D.global_position` 为实体参考位置，验证其从地图内连续越过四条逻辑边界，并能在外侧停留；恰好落在边界线上不满足越界断言。不使用精灵中心、脚底锚点或阴影像素代替该位置。
- **0.2 物理判定**：以 D06 保留的根 `CollisionShape2D` 的实际世界形状与四边碰撞内侧的接触为准，包含圆半径 `7` 和局部偏移 `(0,-6)`。停止位置按形状及其变换核对，不要求玩家根节点恰好停在边界线上，也不能只检查根节点未出界就宣称没有穿透；继续验证四边、四角和沿边滑动，禁止坐标钳制、传送或 `MapBounds` 回位代替物理阻挡。
- **验收范围**：脚底锚点用于人工观察角色外观与地图的对齐，不作为越界或物理断言真源。本决策只冻结阶段 0 的矩形边界验收语义，不扩展为阶段 1 正式地图格式或完整 WAD 墙线碰撞规则。

### 3.4 Collision layers / 碰撞层

现有玩家场景的根 `CharacterBody2D` 使用 `collision_mask = 256`，即查询地图墙体层；原版 `FloorWall` 使用同一墙体碰撞层（`scenes/player/momoi/momoi.tscn:260-264`、`scenes/main/main.tscn:252-258`）。阶段 0.2 按 D03、D06 沿用这一物理层语义。

0.1 的“无碰撞”必须同时验证：

- 玩家本体的场景碰撞形状不参与物理查询。
- 地图边界没有启用可阻挡角色的静态形状。
- `collision_mask` 或其它接触路径不会让角色被测试场景中的隐藏节点阻挡。

0.2 只允许新增矩形地图边界的静态碰撞。碰撞形状必须位于地图边缘，而不是用一张覆盖整图的不可见阻挡面替代四边几何。

## 4. Stage 0.1 / 无碰撞矩形地图

### 4.1 Implementation target / 实现目标

- 创建一个被固定到阶段 0 角色资源的玩家实例。

#### 4.1.1 Files and lookup / 文件与查找规则

- 阶段 0 必须同时读取本地用户提供的 `E:\ETN_DOOM\etndoom_mod\wad\DOOM2.WAD`（IWAD）和 `E:\ETN_DOOM\etndoom_mod\wad\MAP01.wad`（PWAD）。`DOOM2.WAD` 是运行时外部依赖，不复制进模组包或发布物；两份 WAD 的开发源位置按 D10 固定在该目录。
- 阶段 0.3 的回归还必须分别加载同目录的 `MAP01_BackWall.wad`、`MAP01_FrontWall.wad` 和 `MAP01_Texture.wad`；它们是固定测试夹具，不是可选演示图。`MAP01.wad` 保留为最简地图基线，另加用户于 2026-10-30 提供的 `MAP01_HTest.wad`（50mu 高台主体高度验证），五张图均不得用场景内手填参数替代真实 WAD 字段。
- WAD 文件读取采用低复杂度路径：每个 WAD 读入内存一次并建立 lump 目录索引；之后只按需查找和解码当前地图实际请求的资源。这里的“按需”指不解码无关资源，不要求实现逐 lump 磁盘流式读取或遍历/转换整个 IWAD。
- 全局资源 lump 按 IWAD → PWAD 的顺序解析，同名资源由后加载的 PWAD 覆盖；地图结构 lump 则从 PWAD 的 `MAP01` 标记按地图记录顺序读取，不对 `THINGS`、`LINEDEFS` 等通用名称做跨地图全局查找。

#### 4.1.2 Resources and rendering / 素材与显示

- 阶段 0 支持四张回归图实际请求的 `PLAYPAL` 第 0 号基础调色板、`FLOOR0_1`、`CEIL1_1`、`DEM1_5` 平面，以及通过 `PNAMES`、`TEXTURE1` 和被引用 patch 合成的 `STARTAN2`、`BROWNGRN`、`MIDGRATE`、`SLADPOIS` 墙面纹理。当前 IWAD 中 `FLOOR0_1` 为 64×64、`STARTAN2` 为 128×128；`CEIL1_1`、`DEM1_5` 只作为地图/夹具的 flat 输入，阶段 0 不绘制常规 sector ceiling。其它资源类型不在支持范围内；缺失或遇到不支持的纹理定义时须报出资源名与原因，不静默替换。
- 0.1/0.2 画面采用 2D 正交俯视原型，不实现 DOOM 的透视墙面、天花板渲染或光照。地面使用 `FLOOR0_1` 按原尺寸平铺；边界使用 `STARTAN2` 作可辨认的俯视调试表现，其描边/边带仅属视觉，不是 DOOM 墙面的等价渲染，也不得用来推导逻辑边界。纹理使用 nearest 过滤，禁止非等比拉伸地面纹理。0.3 的墙体、地面和角色表现不由此 2D 画布排序实现，改由 3D 深度缓冲实现，详见 0.3 视角契约。

#### 4.1.3 Coordinates and bounds / 坐标与逻辑范围

- 地图坐标固定转换为 `godot_x = wad_x`、`godot_y = -wad_y`；WAD 世界原点 `(0, 0)` 对应 Godot 世界原点，不按地图包围盒重置原点。当前 `MAP01.wad` 顶点范围为 x `[-640, 384]`、y `[-512, 512]`，玩家出生点为 `(-128, 0)`；这些数值作为当前测试图的回归锚点，不是通用地图限制。基础比例为 1 个 WAD 地图单位对应 1 个 Godot 世界单位，因此平面纹理在基础缩放下保持 1 texel 对应 1 地图单位；相机 zoom 只改变观察范围，不改变地图数据、出生点或碰撞的坐标映射。初始视图以变换后的玩家出生点为中心；相机由测试场景独立持有，具体约束见 D07 / §3.3.2。
- 本文的“世界原点”指 WAD `(0,0)` 的映射；“矩形范围”指映射后的 `min_x/max_x/min_y/max_y`，不把其左上角误当作新的世界原点。宽高从边界差值派生且必须为正，边界坐标本身允许负值。当前图宽高为 `1024×1024`；这些数值只用于核验读取结果，不另写一套场景几何。

#### 4.1.4 Validation / 资源与映射验证

## 5. Stage 0.2 / 同图真实静态碰撞

### 5.1 Implementation target / 实现目标

- 复用 0.1 的同一份地图数据、素材、原点、相机和固定角色。
- 通过 `collision_enabled=true` 启用玩家根形状及墙体 mask，并生成矩形四边静态碰撞；其余地图、移动和显示配置与 0.1 一致。
- 不新增敌人、武器、技能、跳跃、刷怪、导航或其它实体。
- 隔离 `MapBounds`，确保角色停止是由物理碰撞产生。

**D03 的生成约定**：

1. 从 `MAP01.wad` 读取地图后先取得并校验同一份逻辑矩形范围：原点、正的宽度和高度；通过 D02 约定的坐标映射确定四条边的位置。边界开闭和 0.1/0.2 的判定标准按已确认的 D08 / §3.3.3 执行。
2. 0.1 和 0.2 使用上述同一份数据及同一组素材。0.1 不创建或启用边界碰撞；0.2 在运行时沿四条边构建一个 `StaticBody2D` 和四个有非零厚度的边缘 `CollisionShape2D`（如 `RectangleShape2D`）。形状的内侧贴合逻辑边界，墙体厚度向外扩展，四角衔接不得留下角色能穿过的缝；不在场景文件中维护第二套边界坐标。
3. 边界使用现有 `wall` 层（bit `256`），由测试角色的 `CharacterBody2D` 以 `collision_mask = 256` 和 `move_and_slide()` 接受物理阻挡。按 D06、D08，以实际碰撞形状的半径、偏移及世界变换核对停止位置，不要求根节点恰好落在边界线上；不通过钳制坐标、传送或 `MapBounds` 回位纠正结果。
4. 自动测试核对两模式读取的原点与宽高一致、四边内侧位置与数据吻合、0.1 无有效边界碰撞、0.2 四边和四角不可穿透且沿边能滑动；人工检查素材与碰撞内侧对齐。素材像素尺寸或贴图空白边若与数据不符，应报告或修正显示映射，不得悄悄改用素材尺寸作为碰撞真源。

阶段 0 只验证矩形外框，不实现任意 WAD 墙线、双面线开口、台阶或高度通行。后续 Godot 物理与 DOOM 空间规则的分工留到阶段 1；原研究说明及源码入口保留在[历史附录 B.3](STAGE_0_DECISION_HISTORY.md#b3-future-wad-collision--后续-wad-碰撞研究)，不作为本阶段依赖。

### 5.2 Manual acceptance / 人工验收

1. 用阶段 0.2 命令启动测试。
2. 确认日志显示与 0.1 相同的地图和角色，并显示 `collision_enabled=true`。
3. 分别正面接近上、下、左、右四条边，确认角色不能穿过边界。
4. 从四个角分别斜向移动，确认角色不会穿过角点，也不会被角点弹飞或卡死。
5. 沿四条边平行移动，确认角色可以连续滑动，不会被不相干的另一条边吸住。
6. 将角色贴近边界后改变方向，确认能够正常离开边界。
7. 比较逻辑边界、地图显示和实际根碰撞形状的停止位置，确认四边内侧对齐；脚底锚点只辅助观察，不要求脚底或根节点恰好停在边界线上。
8. 确认 0.1 与 0.2 的地图表现和角色初始位置一致，差异只有碰撞是否启用。
