## 3. Architecture / 建议的职责边界

| 层 | 拥有的状态与职责 | 对外接口方向 |
|---|---|---|
| DOOM 内核 | 地图装载及资源覆盖语义、实体、位置、碰撞、血量、武器、AI、随机数、机关、sector 状态、关卡进度和游戏存档 | 消费每 tic 输入，输出世界快照与事件 |
| 桥接层 | 内核会话、固定步进、输入队列、稳定实体 ID、资源句柄、错误与生命周期 | Godot → 输入/会话命令；内核 → 快照/事件/资源数据 |
| ETN/Godot | 模式入口、菜单、输入采集与映射、俯视绘制、动画、HUD、音频、显示插值、用户设置 | 读取内核状态；设置类操作与玩法命令分开 |

**一份玩法真值**是新路线的核心：Godot 不再独立裁决同一实体的移动、命中、死亡或机关触发。镜像节点可以保留视觉组件，但不能自动运行 ETN 原玩家/敌人的伤害、刷怪、对象池或回合逻辑。

桥接契约在 M1 至少明确：

- 保留选定内核的模拟节奏与数值语义，经典 DOOM 为 35 tic/s；高显示帧率用插值实现。暂停、失焦、长帧和补 tic 的处理单列，不用改 `dt` 或无说明地跳过 tic 维持画面帧率。
- 输入转为内核命令；屏幕方向移动应先转为世界方向，再依据玩家朝向生成前进/横移等命令。直接写玩家位置、沿用旧 `525mu/s` 求解器会绕过内核行为。
- 坐标与角度只转换一次。当前表现链是 WAD `(x,y,z)` → 逻辑 `(x,-y,z)` → Godot `(x,z,-y)`；朝向、鼠标射线、贴图方向和原点偏移一并验证，不能只核对位置。
- 快照携带 tic、会话/地图代次和实体 ID；传送、出生、死亡与换图明确中断插值。内核指针不作为可跨重开保存的 Godot 身份。
- 明确 ABI/接口版本、数据类型、内存所有权、线程、缓冲区寿命和错误返回；如使用序列化，约定字节序。关键事件不静默丢弃，队列溢出、迟到和重复消费都有可观察处理。
- 初版优先单线程、有界批量传输；每 tic 传快照/增量，避免逐实体逐字段跨语言调用。线程化须由性能测量证明必要后再加入。
- 会话销毁、回到菜单、重新建会话与 DLL 卸载分别定义；不把原生库可热卸载设为重复进入的前提。暂停和时间缩放不能泄漏回 ETN。

最接近的本地参照是 IsoDoom 的独立模拟层与 Godot 表现层，见 `E:/isodoom/docs/SPEC.md:55`、`:65`；它使用 C#/.NET。此处借鉴分层，不把其运行时或作者报告的兼容能力视为 ETN 已验证能力。以上外部目录仅作研究参照，正式构建不得依赖它们。

## 4. Assessment / 对精简建议的实际评估

**结论：建议的主要方向成立，应重组路线；“成功移植”必须指完整玩法运行时已接入，而不是仅加载 DLL 或调用一次关卡 tick。** 原版玩法的实现随源码继承，移植工作负责让其在 ETN 中完整执行、输出状态和恢复生命周期。后续新增开发应集中在内核没有提供的宿主接口、俯视表达与 ETN 特色。

### 4.1 Inherited Capabilities / 哪些能力应直接继承

| 能力 | 本轮源码证据 | 本项目所需工作 |
|---|---|---|
| 玩家移动、怪物 AI、武器、伤害、拾取、机关 | `linuxdoom-1.10/p_tick.c:130` 推进玩家、thinkers 与 specials；`p_pspr.c:647`、`p_inter.c:339,775`、`p_enemy.c:668` | 保留实现及其依赖，接输入与输出；用代表性案例验证继承，毋须重新开发每种玩法 |
| 普通/秘密出口、换关、结算/结束状态 | `g_game.c:605` 的 `G_Ticker()` 调度游戏动作和不同 gamestate；`G_DoCompleted():1020`、`G_DoWorldDone():1172` | 保留游戏流程层；对接宿主场景、显示和确认输入，而不重写关卡推进规则 |
| 存读档 | `g_game.c:1201,1270` 调用玩家、世界、thinkers、specials 的归档/恢复 | 保留序列化能力；适配文件路径、命令入口、版本/资源身份及加载后表现重建 |
| 多 WAD 与外部 PWAD 装载 | `d_main.c:938` 处理 `-file`；`w_wad.c:292` 装载多个文件，`:351` 反向查找使后加载 lump 优先 | 复用内核装载和覆盖语义；补 ETN 文件选择、路径、配置、错误提示及发布流程 |

上表中的 `linuxdoom-1.10/` 路径均相对于只读研究目录 `E:/DOOMSourceCode/`。这些已存在于经典源码中的能力足以支撑重组结论，不需要把它们当作后续新增玩法。具体候选版本的扩展格式和兼容选项仍在 M0 核对。

**外部 WAD 应拆成两层看待**：原生 PWAD 装载已有实现；用户在 ETN 中选择文件、排列加载顺序、检查依赖并正确呈现地图，是集成与产品工作。不能将“外部 WAD”整体列为内核不支持的新功能，也不能从支持 `-file` 推出支持任意节点、脚本或制图技巧。

### 4.2 Remaining Work / 不能随玩法内核自动完成的部分

- **完整流程的移植范围**：`P_Ticker()` 只推进关卡，`G_Ticker()` 还分派装图、重生、存读档、结算与结束等状态。只提取 `p_*` 而丢弃游戏流程层，会人为留下“后续再做完整游戏”的缺口。
- **系统依赖适配**：文件、时钟、输入、音频、错误退出、内存和全局状态重置仍需适配。经典 `G_DoLoadGame()` 在恢复后调用 `R_ExecuteSetViewSize()` / `R_FillBackScreen()`（`g_game.c:1247–1251`），说明已有存档算法也不是无依赖的即插即用接口。
- **俯视呈现**：门在内核中已经运动，不意味着现有 Godot mesh 会更新。当前 `etndoom_mod/stage03/map_view.gd:42` 按读入高度构建几何；玩家 `stage03/player.gd:33` 仍由 Godot 移动。动态几何、所有实体镜像、朝向、遮挡、插值和鼠标输入需要真实接入。
- **宿主界面和反馈**：血量与武器状态已经存在，ETN HUD、菜单、音频输出和加载/结算显示不会自动出现。可保留上游兼容组件或做适配器，按依赖成本选择，避免无必要的全面重写。
- **运行验证**：代码继承可减少算法开发，但裁剪依赖、重置、资源覆盖和输入转换仍可能产生回归。检查贯穿移植及俯视接入，不再独立铺成几个“大规模玩法实现阶段”。

IsoDoom 也显示了这个边界：`E:/isodoom/src/Sim/World.Game.cs:154` 保有完成关卡逻辑，而 `src/Game/GameFlow.cs:24` 的 `IGameHost` 仍要求宿主提供装图、关卡步进、显示和存档加载入口。这是结构证据，不是 ETN 中已成功移植的证明。

历史（2026-11-16）：当时未编译或运行移植原型；读取此前锁定的 Crispy/DSDA 上游源码时网络连接被重置。SUPERSEDED: 2026-11-18，Crispy 固定源码已在本仓构建，M0 自动与人工验收均完成；其它候选不因此新增实测声明。**可以确认阶段归属应调整，尚不能量化移植工期、俯视工作量或承诺“移植完立即全部可玩”。**

建议采用 **M0–M4**：**选型 → 完整内核移植 → 俯视接入 → ETN 增量 → 交付验证**。M0 已完成，M1 实现完成、验收未完成，M2–M4 待完成；完整继承的代表性兼容回归从 M1 开始，M4 扩大矩阵并收口。各阶段工作量不按编号平均分配，前期重点放在 M1。

### M0 Selection / 选型与边界

实施细化见 [M0 文档总览](M0/README.md)：按 M0.1–M0.6 拆分基线、候选、完整范围、桥接、探针和交接，并附候选/构建清单、模块边界、桥接 v0、D01–D10 迁移表及 P0–P5 验证计划。该目录已补齐实际构建锁、R01–R15 源码审计、运行证据与人工结案。SUPERSEDED: 2026-11-18，原“仍为建议稿”已由已完成的 M0 技术基线取代；G1 仍待裁定。

本轮按用户指定比较 Chocolate Doom、Crispy Doom、Boom 与原始 PrBoom，以近期 Vanilla + limit-removing 目标、完整流程及实际可移植性推荐 Crispy Doom；DSDA/PrBoom+ 不混入原始 PrBoom 的能力。原始源码作行为参照，IsoDoom 作分层参照。M0–M1 先实现一个后端，用户已确认 Crispy 为首个内核；先完成其实际宿主接口，未来接入第二个内核时再按实情复用或调整，不预建完整通用适配框架。

重点交付“**保留模块与宿主替换点清单**”：除了 `p_*` 玩法，还需覆盖资源装载、`g_game` 类游戏流程、存档、配置及被玩法依赖的渲染元数据。逐项列出保留、包装、平台替换和真正新增的工作。核实具体版本的节点/补丁格式、许可、平台、重置能力及构建依赖。

优先试验 C/C++ + GDExtension。M1.1 的窄接口探针可作为选型证据，但它通过不代表 M1 完成。若既有宿主加载边界不可满足，先说明失败点再比较替代方案，不自动改变本体或发布方式。旧 D01–D10 中影响选型的冲突在此识别，不拖至移植完才处理。

### M1 Full Runtime Port / 完整玩法运行时移植

实施细化见 [M1 文档总览](M1/README.md)（2026-11-19，已实施，自动证据与人工待验收分别记录）：沿用已完成的 M0，按 M1.1–M1.6 拆分任务，并分别细化桥接、完整流程/存档、平台/音频与验证矩阵；现有 WAD 许可和用途保持，缺失样本另列待落实。

**新增资源许可（2026-11-19，来源：user）**：M1 回归必须分别验证 `doom.wad`（The Ultimate Doom）单独正常运行，以及以它为 IWAD 加载 `dss/DSS.wad`（Dead Sea Scolls）正常运行；DSS 使用 Crispy 默认读取的内嵌 DEHACKED，外部 `DSS.deh` 仅参考、正常情况下不加载。完整清单见 [M1 验收 §2.1](M1/M1_VALIDATION.md#21-approved-additions--m1-新增获准资源2026-11-19)。这是获准具体资源的接入与验证，不将 D08 通用资源功能提前到 M1；2026-11-19 两组自动运行回归均已通过，证据见 M1 验收 §8；人工验收仍未完成。SUPERSEDED: 新增许可时尚无移植运行结果的状态。

M1 是主开发阶段，按以下工作包推进；包间可以迭代，不要求完成全部重构后才进行集成。

| 工作包 | 工作内容 | 可检查结果 |
|---|---|---|
| M1.1 构建与加载 | 固定内核/工具链版本，通过现有 ZIP、PCK entry 和原生库路径加载 | 真实 ETN 发布版输出版本/路径，创建并销毁最小会话；仅算接入探针 |
| M1.2 平台与资源 | 适配文件、时钟、输入、内存、错误处理和媒体输出边界；接获准的必需资源 | 获准资源可运行，内核与表现使用一致数据；D08 通用资源能力归 B2/M3 |
| M1.3 玩法运行 | 保留实体、AI、武器、拾取、机关、随机数及固定 tic，导出输入和状态接口 | 原有玩法在 ETN 内实际执行；不按武器/怪物种类重新开发规则 |
| M1.4 游戏流程 | 保留/适配难度、重生、普通/秘密出口、跨图、结算/结束、暂停及存读档 | 完整游戏状态机推进，存档恢复后状态一致；无关键流程空实现 |
| M1.5 宿主桥接 | 地图/实体快照、事件、资源访问、暂停、失败返回、会话重置和资源释放 | 显示层可消费状态；可退出再进入，输入/事件/宿主状态不泄漏 |
| M1.6 继承验证 | 对照参考构建检查获准资源上的代表性玩法、流程、长帧与重开；通用 PWAD 覆盖专项归 B2/M3 | 提供通过项、差异、缺口与证据，形成“内核移植完成”的依据 |

验收使用同一 WAD、版本、兼容设置、随机初态与逐 tic 命令，核对位置、生命/弹药、实体状态、sector 高度和事件时序。覆盖普通与秘密出口、死亡重开、暂停恢复、跨图和存读档；不只验证走动或单图加载。关卡内机制用少量专项图覆盖代表性类别，不需要为验证继承而重做全部武器/怪物。

此阶段不强制先完成最终俯视画面。可通过真实 ETN 内的诊断视图、状态记录和固定输入验证；若保留原版画面输出成本低，可作为临时对照入口，但不为临时第一人称呈现另开大型开发项目。内核自动验证与最终玩家试玩分别记录。

重复进入以销毁游戏会话为目标，DLL 不必热卸载；检查全局状态、事件、资源、暂停和时间缩放。缺 IWAD/库、ABI 不匹配及可恢复装图错误应返回可操作状态；进程崩溃算失败，不能宣称可由普通返回值恢复。

**完成口径**：已选范围内的原有规则和完整单人流程已在 ETN 运行、可驱动、可观察并有代表性验证，后续主要任务是表现与增量适配。缺失的关键流程必须仍列为 M1 未完成，不能转记成移植后的“新玩法”。

### M2 Top-down Integration / 俯视表现与操作接入

把阶段 0 的相机、坐标、Momoi 显示基础接到 M1 快照和事件上。开发重点是：

- 地面/墙面、上下墙/中墙、动态 floor/ceiling、贴图/灯光/开关变化与天空的呈现。升降台、压碎机和传送的规则已在内核，新增工作是正确显示及插值。
- 全部声明范围实体的镜像、帧/朝向、生成/销毁、遮挡与音效；HUD 和结算界面读取内核状态。数据驱动可共用的表现不按实体重复开发。
- 屏幕方向移动、鼠标朝向、攻击、使用、切武器与暂停输入；命令送入内核，不写位置绕过移动。先使用原内核攻击语义，对照验证后再讨论规则变化。
- 俯视下的天花板/前墙可读性、不可见通道及特殊制图技巧。隐藏遮挡物不能改变碰撞；表现素材尺寸不覆盖内核需要的逻辑元数据。

先用一张小图展示“出生 → 战斗/拾取 → 钥匙门 → 出口 → 重开”，尽早交付试玩，再扩展表现覆盖；这是一条集成验收链，不是重新实现这一组玩法。用高低地、门/升降台和传送案例核对逻辑、画面与输入一致性。

这里仍可能有实质工作量：现有表现只验证五张固定夹具，完整内核不会自动把它扩成任意地图的动态俯视渲染器。因此精简原 M2–M4 的玩法开发，不等于预先认定新 M2 很小。

### M3 ETN Extensions / ETN 特色与产品增量

在可运行、可对照的俯视版本上完善角色替换、光环、动画衔接、菜单、控制提示与界面。此前已用于基本操作的 HUD/音频接口在此打磨，不重新承担内核规则。

SUPERSEDED: 2026-11-16，原“外部 WAD 通用基础装载在 M1 必须接通”调整为：M0/M1 先保证获准资源可运行，D08 全项为 B2/M3。此处再接通/验证通用 PWAD 与其它资源能力，以及用户选择 IWAD、排序 PWAD、记住配置、依赖/资源诊断等交互；复用 Source Port 自带装载器。中文/空格路径与文件错误仍是必需资源接入要求，不能等 UI 完成才验证。

ETN 三维攻击、范围近战及其它规则增量延期到 M3，按明确范围验证。跳跃只使用 Source Port 原生功能：支持则在移植时保留并验证，不支持则功能保持 B2 待评估，不移植 ETN 跳跃；姿态、光环滞后、起跳烟尘与音效为 B2。旧天空决策与原自研导航/刷怪/突袭方案已丢弃，由 Source Port 决定行为，不作为 M3 待实现需求。旧 D01–D10 的具体去向以迁移补充表为准。

建议保留开发用原规则对照配置。是否把它做成与 ETN 扩展并列的玩家模式仍待确认；每项规则改变记录影响，存档记录适用配置。纯视觉替换与玩法变化分开验收。

### M4 Verification and Delivery / 验证与交付

将 M1/M2 已建立的回归扩展到原版代表图、机制专项图及特征明确的 limit-removing 第三方图。分别记录“内核能装载与推进 / 俯视正确呈现 / 交互可完成”，避免只靠加载成功宣称兼容。节点、DeHackEd/BEX、资源替换等以选定版本与实际验证为准；limit-removing 不是通用格式保证。

验证完整游戏流程、存档资源/版本身份、性能、高实体数和复杂几何、重复换图与长时间会话。测量内核 tic、桥接、mesh 更新、绘制和内存，按目标机器预算定位瓶颈；性能回归自前期开始，不留到交付才首次发现。

完成干净环境安装、启用、重启、升级、禁用和卸载；交付模组包、支持范围、已知限制、控制说明、诊断方式及授权/源码材料。构建及必要依赖可复现，不依赖其它本地源码目录，商业 IWAD 由玩家提供。测试和产物按仓库约定仅在本地保存，文档记录可重现命令与证据摘要。

## 7. Evidence / 验收与范围控制

每阶段区分“计划、代码完成、自动验证、真实发布版/人工验收”。本轮来源是源码复核与规划推导，没有移植运行结果，也未将用户假设记成已确认的技术事实。

M1 固定命令发生分歧时定位最早 tic，检查初始化、随机数、时间、资源顺序和裁剪依赖；不靠逐图补丁掩盖。内核规则通过而俯视不正确，归 M2 表现缺口；新增规则破坏已通过地图，归 M3 的兼容取舍。分类用于定位工作，不用于跳过失败。

M0 后复杂地图更多依赖人工验收，MAP02/NoBorder 仍保留基本可验证的自动回归；Stage0 比例、坐标投影及基本遮挡继续作表现基线。地图特例永远是优先级最低的解决方案。任何样本的列举都不构成加载许可。

选定内核上游本就没有的功能才进入新增规则或后续内核升级清单。Boom/MBF21 仍在首版之后评估，不能用路线重排提前承诺。
