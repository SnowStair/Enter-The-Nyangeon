## 1. Rules / 怎样处理冲突

M0 基本需求是 **ETN 中能运行一个移植 DOOM**；俯视功能本身不属于 M0。旧契约保存历史，已被本次新裁定替代的条款不再约束新移植路线；当前 Stage0 的既有实现和验收证据保留。M0 探针使用原规则配置及用户明确允许的 WAD，不因文件已在本地而取得加载权限。

每项拆成：**原用户需求 → 候选实际行为 → 需求是否仍需保留 → 对应阶段 → 决策来源与验证**。§2 原表的“建议”仅为历史；新增 §2.1 表记录当前裁定。候选行为没有版本证据时记未知，不把经典源码直接当作选定内核行为。

阻塞分三类：

- **B0：M0 收口前必须解决**。影响主候选、唯一玩法真值、资源装载或公开承诺；允许继续隔离探针，不允许冻结相互矛盾的正式 M1 契约。
- **B1：特定消费者实现前必须解决**。不一定阻塞候选，但影响输入/快照/表现边界；至少冻结稳定边界与后续裁定时点。
- **B2：留到 M3 的产品/规则增量**。记录“仅延期，不取消”、兼容风险及验收去向；用户已明确丢弃的旧方案不再作为延期需求。候选不支持跳跃时，跳跃功能保留为 B2 待评估项，不据此移植 ETN 跳跃或承诺自研补齐。
