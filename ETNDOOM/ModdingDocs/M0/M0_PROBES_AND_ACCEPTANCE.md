## 1. Evidence Boundary / M0 与 M1 的验收分界

M0 要证明选定方案能在真实宿主中形成最小真实调用链，并给出完整移植的可执行边界。M1 才证明完整单人游戏运行时及代表性玩法/流程继承正确。两阶段共享探针成果，不能将同一次验证重复算成完整实现。

> Revision / 修订（2026-11-16）：M0 基本需求为“ETN 中能运行一个移植 DOOM”。根据 [迁移裁定](M0_LEGACY_MIGRATION.md) §2.1、§3–4，D08 全部 B2，PWAD/其它资源通用能力不阻塞 M0；俯视为 B1/M2。所有实际装图，包括参考构建、夹具及其依赖，只允许用户明确给定并允许的 WAD；当前获准组合及用途见 §4.1（2026-11-17）：`DOOM2.WAD + MAP01.wad` 与单独 `DOOM2.WAD`。不以自动发现或回退加载扩大许可。

| 检查 | M0 要做到 | M1/M2/M4 仍需做 |
|---|---|---|
| DLL/扩展加载 | 真实安装、类注册、身份读取、最小会话 | 正式模块与全依赖打包、完整生命周期 |
| 装图与步进 | 实际资源、实际完整调度入口、固定输入、最小快照 | 战斗/机关/特殊图、完整游戏流程 |
| 反复重建 | 少量会话、资源切换、暂停/错误可观测 | 长时/多图、存读档、压力与内存稳定性 |
| 更新/卸载 | 所选原生部署路线有一次真实验证或失败证据及已验证替代 | 干净环境与版本组合的完整矩阵 |
| 兼容与性能 | 样本/对照方法锁定，取得早期测量 | 支持范围内全面覆盖、最终预算验收 |

## 2. Environment / 隔离环境与证据身份

复用 [ETNDOOM/MOD_TESTING.md](../../MOD_TESTING.md) 的安装、重启票据和隔离思路；先核对现有工具适用范围，不假定它们已经认识原生库或新 Mod ID。

- 执行前确认实际 `user://` 位于本地测试目录，避免写入玩家正式配置/存档；确认隔离环境能传到真实 exe。仅设置环境变量但未读回路径，不算隔离成功。
- 源码工程、干净安装目录和真实发布 exe 分别记录身份。源码模式可调试，但不能替代发布版加载证明。
- 从真正 ZIP 安装、启用并重启，再通过模组 entry 运行。entry 为 deferred，等待带超时的完成标记，不只等待固定一帧。
- 避免工作区 `mods/` 或共享 `.godot` 缓存掩盖包内缺文件；真实发布版验证不借用开发机源码/依赖搜索路径。
- 现有测试监督器共用隔离工程缓存时串行执行；无需为文档准备实际运行游戏。

## 3. Probes / 按风险顺序执行

### P0 Host Baseline / 宿主与隔离基线

**输入**：目标真实 ETN exe、现有最小模组入口、独立测试用户目录。

**步骤**：记录 exe 哈希/版本；启动后读引擎版本、架构、feature 和实际 `user://`；核对 ZIP 安装/重启/entry 顺序；记录当前模组清单；确认未进入 DOOM 时本体菜单仍可用。

**通过**：宿主身份可定位、隔离路径已核对、entry 可观察、无误写正式存档。缺引擎/API 身份则不能以开发机编辑器版本代填。实际 ABI 匹配留 P2 验证。

### P1 Reference Build / 暂选候选的参考构建

**输入**：固定源码 commit、工具链、依赖、配置及用户明确允许的 WAD；拥有文件不等于允许本次加载。

**步骤**：先按上游支持方式构建可运行参考；保存完整命令、返回码、产物哈希；启动同一地图与配置。若比较两个候选，只要求暂选候选先完成本探针，另一个仍可保留静态证据，但必须如实标记。

**通过**：从新构建目录可重复得到可运行版本，能装图并推进。若为差分加观察钩子，保存单独补丁、说明仅记录状态且不改变 RNG/时序；参考不得复用待测适配器来计算期望值。

上游程序不一定暴露逐 tic 命令注入；M0 必须选定可实现的参考方式（最小记录/注入钩子或已核实的输入回放能力），不因支持 demo 就假定可以录制当前俯视输入或完整兼容所有 demo。

### P2 Native Host Load / 真实宿主原生加载

**输入**：按拟定布局构建的 ZIP、最小 GDExtension 库、所需依赖。此阶段可先不链接完整内核，以分离宿主限制。

**步骤**：通过现有安装器安装 → 重启 → PCK entry → 定位物理扩展文件 → 加载并检查返回状态 → 查询构建身份/注册类 → 调用一次最小接口。记录实际解析路径和库哈希。

**通过**：真实发布 exe 内运行成功；无需改本体、启动器或依赖其它源码目录；中文/空格安装路径可用。仅编辑器/headless 工程成功、手工放 DLL 到 exe 旁成功、只打印 entry 日志均不算通过。

**反例**：缺主库、缺一项动态依赖、ABI/架构不匹配、无效扩展路径；应在进入玩法前给可定位诊断并保持菜单可操作。依赖类型的脚本必须在扩展成功后加载，避免解析阶段就失败。

### P3 Minimal Core Chain / 最小真实内核链路

**输入**：暂选内核的薄包装、P2 已通过布局、一张基础图及相同参考资源/配置/输入。

**步骤**：建会话 → 新游戏/装图 → 读静态地图与初态 → 固定输入推进 → 每 tic 读取最小状态 → 暂停/恢复 → 销毁 → 再建。建议先零输入，再加入有阻挡/跨线的短移动序列，避免只测试不触及规则的空循环。

建议最小规模为每段 **350 tic（35 tic/s 下 10 秒模拟时间）**，静止与移动各一段；该数量可根据实际风险调整并记录。参考比较至少含玩家原始位置/动量/角度、实际 gamestate、可取得的 RNG 状态、实体数量、sector 高度与输入消费范围。字段未能导出就记缺口，不能以 `0`/固定值补齐。

**通过**：真实 ETN 内的地图/推进来自所选内核，同资源/命令与参考一致；能读出内核状态并清理重建。不能直接调用一个空 `tick`，也不能只用 `P_Ticker()` 的运行结果宣称完整流程已接通。完整流程出口实际验收仍在 M1。

首次状态分歧记录最早 tic、字段、预期/实际、输入、资源/配置身份；先排查初始状态、RNG、量化、调度及裁剪依赖，再考虑已明确的上游平台差异。

### P4 Lifecycle and Failure / 生命周期、时钟与失败

**输入**：P3 链路、合法资源 A/B、缺失文件、一个受控损坏输入、可注入显示帧序列。

| 情形 | M0 最小检查与通过条件 |
|---|---|
| 重复进入 | 建议连续 10 次建销会话；无旧实体/事件/输入引用、无重复信号或音频；次数不等于长期无泄漏证明 |
| 资源切换 | 仅在获准清单与最小运行链路内验证；可先以同一获准资源重建对照新进程初态。通用 PWAD/补丁切换专项降为 B2/M3，不要求为 M0 新增装载能力或扩大许可清单 |
| 暂停恢复 | 暂停期间不增加 gameplay tic；恢复不补暂停 wall time、不重放边沿请求；退出仍可操作 |
| 长帧/高刷新 | 不同显示帧序列下执行相同总命令/tic，最终状态一致；人工长帧能看到补 tic/积压计数，不静默丢 tic |
| 失败后重进 | 缺获准 WAD/读取失败后清理部分状态，再次合法建会话可成功；受控损坏地图须单独获准，不擅改获准原件或默认派生文件也获准；未知内存破坏不算可恢复案例 |
| 身份/事件 | 旧代次命令被拒绝；事件重复读不重复播放；队列容量不足有明确状态 |
| 返回 ETN | 菜单可用；暂停/时间缩放/鼠标/音频按进入前状态及所有权恢复；正式存档未被改写 |

记录工作集与内核分配计数、每次销毁后存活对象及留驻缓存。有限次数内没有明显增长只能作为 M0 早期证据；M1/M4 仍需扩大时间与规模。任一 crash/超时由外部监督记录失败，不当作正常退出。

### P5 Native Update / 原生部署的更新、禁用与卸载

**输入**：构建身份不同的 A/B 两个最小包、隔离安装目录、已选加载布局。

**步骤**：安装 A/重启/加载 → 尝试按产品允许流程更新 B → 校验安装事务返回及目录 → 重启 → 读取确为 B 的库哈希/构建身份 → 禁用/重启 → 卸载/必要的待卸载清理。额外验证失败更新不会破坏可用旧安装。

**通过**：用户实际可执行的流程成功，新进程加载正确版本；禁用后不新建内核会话；卸载/缓存残留策略明确且被验证。若运行中更新被 DLL 占用阻挡，应记录为该流程失败，并测试可交付的替代流程后才能关闭问题；不能仅看 PCK 更新成功。

此处只覆盖选型所必需的最小分发风险，M4 仍需对多版本、干净环境、缺依赖、失败回滚和升级后的存档做完整矩阵。

## 5. Differential Method / 怎样证明继承正确

冻结对照构建与端口的资源顺序、兼容配置、初态/RNG、逐 tic 命令；同一份输入绕过实时采集噪声。对照不要求最终俯视画面，也不把图像相似当作规则等价。

原始定点/整数/枚举状态在同配置下应精确比较；快照若有浮点表现值，另列转换容差与依据，不把它混入模拟哈希。比较世界状态应规范序列化顺序，排除指针、padding、wall time 和渲染缓存，保留有意义的 thinker/创建顺序及 RNG 信息。

完整状态哈希只用来快速定位差异，出现不等时仍需输出字段与最早 tic。观察钩子不得调用改变 RNG/状态的查询；渲染开关、日志开关、快照消费频率变化后模拟轨迹应一致。

存读档验证在 M1 比较“不中断继续运行”和“保存→恢复→继续输入”，检查玩家/世界/thinkers/specials/RNG 与后续事件；不能仅比读档那一帧的位置。

## 6. Performance Baseline / 早期性能记录

P3/P4 记录目标 CPU/内存、发布构建选项、地图/实体数、实际采样数量，分别测内核 tic、快照构造/复制、Godot 消费、内存/资源句柄。平均值与 p95/峰值分开；短样本的分位值明确只供初筛。

35 tic/s 对应约 28.57ms 模拟间隔，不等于可把整段时间耗在内核；显示目标帧预算另定，M2 网格/绘制尚未加入时不得声称最终 FPS 达标。M0-D10 在实际测量后填写内核/桥接预算、最大补 tic 与压力回归阈值，M4 再按最终场景验收。

## 7. Failure Routing / 失败归因与停止扩大范围

| 失败 | 优先检查 | 后续行动 |
|---|---|---|
| 参考版本构建失败 | 工具链、依赖、版本与上游构建说明 | 先恢复可重复参考，不在 ETN 里盲调 |
