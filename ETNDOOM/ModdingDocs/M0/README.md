## 1. Goal / M0 要解决什么

M0 基本需求是 **ETN 中能运行一个移植 DOOM**，俯视功能本身不属于 M0。交付包含真实宿主内可运行的最小移植链路，以及能够指导 M1 的决策包：**选定哪份源码、保留哪些完整系统、怎样连接 Godot、怎样证明没有改坏原有行为，以及旧规则如何迁移。** 仅有文档或 DLL 加载成功不能满足基本需求；完整单人流程的全面继承验收仍由 M1 承担。

选型不能只比较支持列表。候选已有的玩法只有在资源、游戏流程、平台服务和生命周期依赖一起保留下来时才构成可移植内核；DLL 能加载也不等于这些条件成立。M0 应优先消除会迫使 M1 大面积返工的风险。

| M0 必须形成的答案 | 后续直接依赖它的工作 |
|---|---|
| 内核仓库、完整 commit、补丁基线、兼容配置 | M1 构建、差分验证、M4 升级与复现 |
| 实际 ETN exe、引擎版本/API、架构、原生库安装与加载路径 | M1.1、全部发布与更新工作 |
| 玩法、完整单人流程、资源语义、逻辑元数据保留清单 | M1.2–M1.4；避免把继承能力遗漏成后续开发 |
| 输入/tic、身份、快照、资源、事件、重置契约 | M1.5、M2 地图和实体表现 |
| 旧 D01–D10 的冲突与迁移处置 | M1 兼容基线、M2 操作、M3 规则变化 |
| 对照版本、样本身份、测试步骤与通过判据 | M1.6、M2 集成验证、M4 支持矩阵 |

## 7. Change Control / 冻结后的变更与交接

内核 commit、兼容选项、依赖版本、宿主 exe、输入量化、快照字段、身份语义或旧规则裁定变化后，重新评估关联门槛；不能只改实现不更新契约。桥接可增加兼容字段，但改变既有含义应升接口版本并更新消费者。

M1 交接至少包含：选型记录、构建锁、保留/替换清单、桥接 v0、规则差异表、获准样本清单、P0–P5 适用项结果与延期项、未决项及阶段归属。不得有“以后再补”的关键游戏流程或无负责人阶段的阻塞项。M0 本身不自动提交 Git；`WORKLOG.md` 仅按仓库规则记录用户敲定的修正或明确要求的总结。
