## 1. Core Conclusion / 核心结论

在现有加载器和 Godot 运行环境内，模组能力大致可以从“只增加内容”延伸到“在游戏进程中运行一套独立玩法”：

- 可以增加角色、敌人、武器、支援、服装、语言、关卡和模式等内容。
- 可以通过 entry、`GameEvents` 和 `ExtensionHooks` 改造转场、回合、伤害、死亡、刷怪、菜单和联机等规则。
- 可以提供自己的场景、脚本、贴图、音频和 UI；必要时使用 `replace_files=true` 覆盖本体资源路径。
- 可以让 entry 加载自己的主场景、输入、实体、规则、UI 和存档，形成玩法层面的完整重制。
- 不能把普通模组等同于修改 Godot 二进制、改变平台启动器、获得任意运行期方法补丁能力，或保证已经初始化的所有本体对象都能无条件替换。

因此，实际能力上限可以表述为：

> **接近“在原有 Godot 进程内运行另一套游戏”，但仍受原生加载时序、本体常驻单例、资源缓存、导出脚本格式和平台能力限制。**

## 2. Loader Boundary / 原生加载器边界

### 2.1 Existing loading route / 现有加载路径

当前原生加载器为 `ModManager`：

1. 扫描 `user://mods/<id>/mod.json` 和 `<id>.pck`；桌面发布版还会扫描 exe 同目录的 `mods/`。
2. 通过 `ProjectSettings.load_resource_pack(pck_path, replace_files)` 挂载 PCK。
3. 延迟加载 manifest 中的 entry，实例化脚本并加入场景树。
4. entry 是普通 `Node`，可跨原版场景切换继续存活。

重要边界：

- `ModAPI` 主要是内容注册和数据扩展接口，不是权限沙箱。
- entry 可以访问场景树和 autoload；因此独立模式可绕开本体的内容注册路线，自行加载 `PackedScene`。
- `KIND_CLASS` 当前没有原生 `maps` 类型。单独增加 `defs/maps/` 不会自动获得原生地图注册和加载能力，地图目录必须由新模式自己的加载层处理。
- `ExtensionHooks` 的通知类信号只表示事件发生，不会自动取消本体逻辑；只有 gate / interceptor 类接管点返回 `true` 时，本体对应分支才会跳过。
- JSON `overrides` 主要作用于已进入 `_registry` 的内容，不能当作对所有直接 `load()`、预加载或场景内部资源引用的全局替换。

### 2.2 Replacement and startup / 覆盖与启动时序

- PCK 覆盖改变的是资源路径解析，不会修改磁盘上的本体文件，也不会自动替换已经实例化的节点、脚本对象或已持有的 `Resource`。
- 本体启动时 autoload 的实例化和加入根节点存在时序；`ModManager._ready()` 挂载模组通常已经晚于部分本体脚本的加载。仅调整 autoload 顺序不能保证所有本体 preload 都被覆盖。
- 导出本体脚本可能使用 `.gdc` 与 `.gd.remap`。覆盖本体脚本时，应按 `ModPackReplace` 和 SDK 规则生成相同的导出格式；只放同名裸 `.gd` 可能仍被 remap 导向旧脚本。
- `replace_paths` 是构建工具的声明，不是运行期覆盖白名单；运行期实际使用 manifest 的 `replace_files`。

### 2.3 Practical modification levels / 实际修改层级

| 层级 | 典型内容 | 主要限制 |
|---|---|---|
| 内容扩充 | 新角色、敌人、武器、支援、服装、关卡 | 需要遵守本体资源类型和消费方契约 |
| 规则改造 | 伤害、死亡、回合、刷怪、转场、菜单、联机 | 依赖现有 hooks、信号和本体初始化时序 |
| 场景替换 | 自带场景、UI、地图表现、材质、音频 | 需要处理资源缓存、依赖和导出格式 |
| 独立玩法 | 自有主流程、实体、规则、输入、UI、存档 | 必须隔离本体常驻单例和全局副作用 |
| 引擎 / 平台层 | Godot 二进制、启动初始化、平台权限 | 不属于普通脚本与资源模组的可靠能力范围 |

## 3. Existing Arena / 原版场地定义

原版场地不是一个单独的、可由原生加载器注册的 `Map` 对象，而是多个场景、TileSet、碰撞层、生成逻辑和边界安全网共同形成的运行环境。

### 3.1 Rendering and collision / 显示与碰撞

- 原版是 Godot 2D 等距投影场景。
- `FloorWall` 提供实际墙体碰撞，使用独立物理层；玩家等实体通过碰撞掩码与其交互。
- `SpawnMap` 主要承担地图格子、生成区域或地图表现相关职责，不能直接等同于真实可行走边界。
- 地图显示位置、物理碰撞形状和实体脚底位置必须分别核对；不能仅凭精灵的屏幕坐标判断场地几何。

### 3.2 `MapBounds` / 出界回位

原版有 autoload `MapBounds`：

- 通过 `GameEvents.global_time_count` 定期检查玩家、敌人和召唤物。
- 优先从场景中心向四个方向查询 `FloorWall` 内壁，构造可行走边界。
- 查询失败时才回退到 `SpawnMap` 的几何范围。
- 出界实体会被移动到边界内最近位置；这不是物理碰撞本身。
- 该逻辑由信号驱动，只关闭 `_process` 不足以停用；新模式进入和退出时必须断开、隔离或避免它处理新模式实体。

因此，新增地图或新模式不能用坐标钳制、越界传送或 `MapBounds` 回位来伪装场景碰撞。阶段 0.1 应明确关闭这类干预，阶段 0.2 才验证真实静态碰撞。

## 4. New Mode and Importable Maps / 新模式与可导入地图

目标设定为：新增一个独立模式，不沿用原版刷怪、突袭出生和寻路逻辑；地图是可导入资源；地形为简单、不叠层的伪 3D。

### 4.1 Recommended runtime responsibilities / 推荐运行时职责

建议由模组内部拆分以下职责：

| 模块 | 职责 |
|---|---|
| `ModeSession` | 管理进入、运行、结束、重开和退出 |
| `MapCatalog` | 发现地图、提供稳定 ID、版本和兼容信息 |
| `MapLoader` | 读取地图包、校验数据和资源 |
| `MapDefinition` | 保存静态地形、障碍、装饰、出生区域和连接 |
| `MapRuntime` | 根据定义创建表现、碰撞、空间查询和导航派生数据 |
| `SpawnDirector` | 按模式规则选择敌人、数量、时机和合法出生点 |
| 实体 / 战斗系统 | 消费统一的地面、高度、通行、遮挡和命中查询 |

地图数据和一局中的实体状态应分离。替换地图应只替换数据和资源，不要求重新编写模式专用脚本。

### 4.2 Simple pseudo-3D rules / 简单伪 3D 规则

第一版建议采用：

- 逻辑平面位置 `(u, v)` 加独立世界高度 `h`。
- 地面高度由 `H(u, v)` 查询；屏幕坐标由等距投影和高度偏移计算。
- 同一平面位置最多一个可站立地面，允许无地面的空洞，不处理叠层平台。
- 离地时独立积分世界高度；不能每帧把当前地面高度直接叠加到跳跃偏移。
- 移动、碰撞、导航、出生点和攻击都消费同一套空间规则。
- 先支持离散高度平台和显式楼梯连接；连续坡面、复杂抛物线弹道和多层重叠后置。

必须在正式实现前裁定：坐标采样、单位、高度等级、最大跨步、楼梯方向、墙体高度、跳跃和落差、空洞处理、攻击高度、鼠标反投影以及不同实体的通行能力。

### 4.3 Import format / 导入格式方向

建议先实现“目录 + JSON + 相对路径图片”，稳定后再增加 ZIP：

- 外部数据在运行期读取，内部统一转换为 `MapDefinition`。
- 地面、障碍、楼梯连接、装饰、素材、玩家出生点、敌人区域和突袭入口均由数据描述。
- 加载时校验格式版本、地图规模、资源引用及玩家起点记录。SUPERSEDED: 2026-11-12，D09 已确认不检测玩家出生合法性，只要求 type 1 存在且记录结构可读取；初始重叠、净空不足或无地面覆盖不作为出生拒绝条件。上文楼梯连接属于历史方向，现按 D03/D07 几何规则处理。
- 碰撞和导航数据优先由地形和连接派生，避免地图作者分别维护互相矛盾的三套数据。
- 不直接把任意 Godot 场景树当成可运行地图；若后续支持 Godot 场景或 PCK 地图包，也应转换或校验到同一数据契约。

## 5. Implementation Order / 实施顺序

阶段 0 是后来插入的前置验证，必须按 `0.1 → 0.2 → 1` 执行；原阶段 1–9 的编号保持不变。

### Stage 0 / 阶段 0：最小地图渲染与碰撞

#### 0.1 无碰撞地图渲染

- 导入一张最简单的矩形平地图。
- 固定使用 `res://scenes/player/momoi/momoi.tscn` 作为测试角色，不依赖动态选角顺序。
- 不生成敌人、召唤物、子弹、掉落物或其他玩法实体；不启动攻击、技能和刷怪。
- 不启用场景碰撞，也不启用原版边界回位或坐标钳制。
- 角色可移动，用于观察地图素材、尺寸、原点、位置、相机和角色显示是否正确。

验收：角色经过地图边缘不会被阻挡、拉回或传送；地图与角色显示位置正确。

#### 0.2 同图加入场景碰撞

- 继续使用同一张矩形地图、同一个固定 Momoi 角色和同样的空实体环境。
- 只加入地图静态碰撞。
- 测试四条边、四个角、沿边移动和碰撞轮廓与画面的位置一致性。

验收：角色被真实碰撞阻挡，沿边移动正常；不能用坐标钳制或 `MapBounds` 回位代替。

阶段 0 只验证平面地图、渲染和静态碰撞，不提前加入高台、楼梯、导航、战斗或完整模式流程。阶段 0 所需只是最小测试入口、外部资源读取、角色移动和相机；原型字段不自动成为正式地图格式。

### Stages 1-9 / 阶段 1–9

| 阶段 | 目标 |
|---|---|
| 1 | 裁定高度、通行、攻击规则和最小地图格式；形成低地、高台、楼梯测试图的数据契约 |
| 2 | 建立新模式运行壳、入口、退出和清理；重复进入不残留状态 |
| 3 | 建立最小目录地图加载器和实例构建；地图文件可独立替换，错误可定位 |
| 4 | 实现高度查询、碰撞、角色移动和表现；图像与判定位置一致 |
| 5 | 实现地图派生导航和测试敌人；敌人能绕障碍、使用楼梯，无法到达时有明确状态 |
| 6 | 实现基础战斗和拾取；验证高度、墙体、命中和掉落 |
| 7 | 实现新刷怪与突袭调度；按地图区域标签出生，失败时有限尝试或暂停 |
| 8 | 组合成完整新模式；完成开始、胜负、重开、退出和跨地图验证 |
| 9 | 完善 ZIP 导入、地图目录、制作工具和版本兼容流程 |

首个战斗闭环仍是后续目标，不是阶段 0 前置：一张包含低地、高台、楼梯和障碍的外部地图，一个角色、一个敌人、一种武器和一种区域刷怪，能够结束、重开和退出；第二张布局不同的地图只增加数据和素材，不增加地图专用脚本。

## 6. Risks and Non-Claims / 风险与非结论

- 本文没有声称完整重制模组已经构建、安装或在发布版运行验证。
- 本文没有冻结地图 JSON 字段、坐标单位、高度单位、攻击高度或导航连接规则。
- 原版玩家跳跃主要是显示层偏移，不等于已经具备地形高度运动能力。
- 原版 `MapBounds`、输入、暂停、时间缩放、全局信号和本体场景切换可能继续影响新模式；进入和退出时必须逐项检查。
- 资源覆盖可能受到缓存、`.gdc` / `.gd.remap`、已实例化节点和本体 preload 的限制。
- 目标平台的输入、渲染、文件权限、发布版引擎模块以及完整重制的实际上限仍需通过最小可运行原型确认。
